# taxi-preflight — проверка предусловий задачи (протокол v1)

Канонический источник этого навыка — файл `.agents/skills/taxi-preflight/SKILL.md`. Адаптер `.claude/skills/taxi-preflight/SKILL.md` только указывает сюда и собственных правил не содержит.

## 0. Статус и иерархия документов

- Нормативный документ — **`docs/agents/PROTOCOL.md` v1**. Этот навык лишь пересказывает порядок проверки и **ничего не добавляет к протоколу и не отменяет в нём**. Если навык расходится с PROTOCOL.md v1, прав PROTOCOL.md v1, а расхождение записывается в отчёт как дефект навыка.
- **`docs/agents/v2/**` имеет статус `DRAFT / NOT ACTIVE`**. Сообщения `CLAIM/2`, `ASSIGN/2`, `RESUME/2`, `HANDOFF/2`, `QA-REPORT/2` по реальным задачам недействительны. Ссылка на v2 как на действующие правила — повод для `BLOCKED (protocol_v2_not_active)`.
- Навык — **процедурная справка, а не полномочие**. Он не выдаёт G0, ASSIGN, RESUME, REASSIGN, G2 или G3, не делает merge и deploy, не меняет labels и статусы. Без явного поручения он ничего не публикует в GitHub.
- Агент **никогда** не составляет и не публикует `OWNER-DECISION` от имени владельца, даже как «черновик для владельца» (PROTOCOL v1 §0.2, §5.6).

## 1. Когда применять

- **WHEN:**
  - перед публикацией `CLAIM` — режим `READ_ONLY_PREFLIGHT`;
  - после `ASSIGN`, перед первой записью (ветка, файл, commit, draft PR) — режим `PRE_WRITE`;
  - перед публикацией `HANDOFF` — режим `PRE_HANDOFF`;
  - когда новая сессия находит задачу в `in-progress` или `blocked` (§8.2) — режим `RECOVERY`;
  - QA-задача перед началом проверки и перед публикацией отчёта: этот навык как первый шаг, затем `taxi-evidence-qa`.
- **WHEN NOT:**
  - для выдачи или подделки решений владельца или координатора (G0, ASSIGN, RESUME, G2, G3);
  - как замена независимого QA — для доказательств есть `taxi-evidence-qa`, для кода нужна отдельная QA-задача;
  - для задач по протоколу v2;
  - для production, планшета, GPS, Car-Jukebox и сервисов: навык их не касается и не разрешает к ним доступ;
  - когда Issue нет и задача сформулирована только в чате: результат `BLOCKED (no_issue)`.

## 2. Входные данные

| Вход | Откуда | Если нет |
|---|---|---|
| номер Issue и Task ID | поручение человека или координатора | `BLOCKED (no_issue)` |
| своя роль (`agent:`) | назначение | `BLOCKED (role_unknown)` |
| фактический ID сессии | платформа (см. §3, шаг S1) | `BLOCKED (session_unknown)` |
| режим | `READ_ONLY_PREFLIGHT`, `PRE_WRITE`, `PRE_HANDOFF` или `RECOVERY` | по умолчанию `READ_ONLY_PREFLIGHT` |
| текущее время UTC | системные часы | при сомнении в часах — `NOT_VERIFIED` для lease |

## 3. Процедура (только чтение)

Все шаги выполняются **заново в текущей сессии** по первичным источникам: GitHub API или коннектор, `git ls-remote`, файлы на закреплённом commit. Цитаты из чата, таблицы координатора и отчёты других агентов — это ожидаемые значения, а не доказательства. Порядок шагов фиксирован. Если обязательный шаг дал не `PASS`, итог не может быть `PASS`.

Используйте только инструменты, разрешённые в своей среде. Например, в облачной сессии Claude Code к GitHub обращаются через MCP-инструменты, а `gh` — только для поиска. Обходить ограничения прокси или сети запрещено: недоступный источник даёт `NOT_VERIFIED`, а не обходной путь.

**S0. Действующий протокол.** Прочитать `docs/agents/PROTOCOL.md` на `origin/<target_branch>`. Убедиться, что v2 помечен `DRAFT / NOT ACTIVE` (`docs/agents/v2/README.md` §1). Любое сообщение задачи с `v: 2` или типом `*/2` недействительно.

**S1. Сессия.** Узнать **фактический** ID своей сессии от платформы, а не придумать его:
- Claude Code Remote — инструмент `get_session` (поле `id`);
- DeepSeek Harness — `DSH_SESSION_ID` и метаданные сессии (`isSeeded`, `inheritedEventCount`, `parentSession`);
- Codex и другие платформы — их штатный способ. Если способа нет, записать `NOT_VERIFIED (session_id_source)` и сообщить координатору до CLAIM.

Раскрыть родительские сессии, общий хост, рабочее пространство и учётные данные, если они есть. Общий аккаунт GitHub `iprus2026-tech` личность **не подтверждает** (§0.1).

**S2. Issue.** Issue открыт. Ровно один label `agent:*`, и он совпадает с ролью исполнителя (§1). **Ровно один** label `status:*`: ноль или два и больше → `BLOCKED (status_ambiguous)`. Этот статус допустим для режима:

| Режим | Допустимый статус |
|---|---|
| `READ_ONLY_PREFLIGHT` | `ready` |
| `PRE_WRITE`, `PRE_HANDOFF` | `in-progress` |
| `RECOVERY` | `in-progress` или `blocked` |

Поиск по Task ID должен находить ровно одно Issue. Текст вне канонической формы (например, устаревший раздел Status) на SPEC не влияет, но несоответствие записывается в отчёт.

**Зависимости (§4).** Если `depends_on` канонической SPEC (S3) — `- none`, проверка `N/A`. Иначе для каждого Task ID найти его Issue: оно должно быть в `status:done`. Нет Issue, статус другой или их несколько → `BLOCKED (dependency_not_done)`. Проверка выполняется во всех режимах, потому что зависимость могла быть переоткрыта после `ready`.

**S3. Каноническая SPEC (§4.2).** Построить `TAXI-ISSUE-SPEC/1` из **текущего** тела Issue:
1. Взять только поля `task_id`, `base_sha`, `depends_on`, `allowed_paths`, `forbidden_paths`, `acceptance`, `gates` из соответствующих разделов Issue Form. Порядок полей — как в списке.
2. Скаляры вида `ключ: значение` без обрамляющих обратных кавычек. Списки — строка `ключ:`, затем строки `- элемент`.
3. В `depends_on` — Task ID без повторов, отсортированные побайтно; пусто → `- none`. В `allowed_paths` и `forbidden_paths` — пути без `./` и ведущего `/`, без повторов, отсортированные побайтно; пояснительный текст после блока путей в форму не входит. `allowed_paths` пусто → `- none`; `forbidden_paths` пустым быть не может.
4. В `acceptance` — элементы `AC-<n>: <текст>`, n = 1..k подряд. Текст в одну строку, последовательности пробелов сжаты до одного.
5. В `gates` — подмножество `G0-intake`, `G1-design`, `G2-merge`, `G3-deploy` в этом порядке.
6. Байты: UTF-8 без BOM, Unicode NFC, только LF, без табуляций, без пробелов в начале и конце строк, без пустых строк, первая строка `TAXI-ISSUE-SPEC/1`, ровно один завершающий LF.
7. `issue_spec_sha256` = SHA-256 этих байтов. Записать длину в байтах.

**Самопроверка реализации обязательна:** проверочный вектор §4.2 (495 байт) должен дать `f9b02543d760371607e263bc8b1f00c0e2030b9d074cf159899f7e716e7456cd`. Иначе — `NOT_VERIFIED (canonicalizer)`, сравнивать хэши нельзя.

Затем сравнить:
- с блоком `issue-spec` последнего действующего сообщения `SPEC` — оно не редактировалось (`created_at = updated_at`), а цепочка `supersedes` прослежена до конца;
- с `approved_spec_sha256` в G0 (S4).

Любое расхождение → `BLOCKED (spec_changed)`. Работа и передача результата прекращаются до новой пары `SPEC` + G0 (§4.2 п.4–5). Старый G0 на новый хэш не распространяется.

**S4. G0 (§5.6, §4.3).** Сначала выбрать **последнее действующее решение** владельца по G0, и только потом проверять, что оно `APPROVE`. Фильтровать по `decision: APPROVE` до выбора последнего нельзя: так более позднее `REJECT` или `CHANGES` было бы пропущено.

1. **Кандидаты.** Все блоки `type: OWNER-DECISION` с `gate: G0-intake`, относящиеся к этой задаче (`task` = Task ID; в G0 на несколько задач — пара `task_id` + хэш этой задачи), **с любым** `decision`: `APPROVE`, `REJECT` или `CHANGES`. Порядок — по `created_at` GitHub, а не по внутреннему `ts`.
2. **Действительность.** Решение действительно, только если выполнено всё: отдельный комментарий, `created_at = updated_at`; `agent: owner`; блок не пришёл в relay от агента и не опубликован агентом; `ts` — корректная метка ISO 8601 UTC; `decision` — ровно одно из трёх значений; у `APPROVE` есть `approved_spec_sha256` в полные 64 hex.
3. **Действующее решение** — последнее по `created_at` **действительное** решение из п.1. Именно его `decision` определяет итог:
   - `REJECT` → `BLOCKED (g0_rejected)`; `CHANGES` → `BLOCKED (g0_changes_requested)`. Так и тогда, когда раньше было `APPROVE`, в том числе по тому же хэшу SPEC. Более раннее `APPROVE` после них прав не даёт, пока владелец не опубликует **новое** `APPROVE` позже. Если `REJECT` или `CHANGES` ссылается на другой хэш SPEC или не указывает хэш, оно всё равно блокирует (fail closed), а расхождение записывается в отчёт;
   - `APPROVE` → `approved_spec_sha256` равен хэшу из S3 (полные 64 hex). Иначе `BLOCKED (spec_changed)`.
4. **Недействительные решения** не дают прав никогда. Недействительное `APPROVE` (отредактированное, от агента или в relay, с некорректным `ts`) пропускается и раскрывается; действующее решение выбирается среди действительных. Недействительное или неоднозначное `REJECT`/`CHANGES` **позже** действующего `APPROVE` молча не отбрасывается: `STOP (owner_decision_ambiguous)` и вопрос координатору и владельцу. Два решения с разными `decision` и одинаковым `created_at` → тот же `STOP`.
5. Несколько действительных `APPROVE` подряд: действует **последнее** по `created_at` (§4.3 п.3). Работа никогда не разрешается только на основании более раннего `APPROVE`, если после него есть более позднее решение.
6. S4 пересчитывается в каждом режиме и в каждой контрольной точке: `REJECT` или `CHANGES`, опубликованное после ASSIGN, останавливает работу при следующем `PRE_WRITE` или `PRE_HANDOFF`.

У действующего `APPROVE` в `note` есть строка `target_branch: <ветка>`; без неё G0 недействителен для ASSIGN (§4.3 п.2). Эта ветка — `target_branch` для S5. Сверить остальные ограничения `note` (роль, scope, запреты) с планируемыми действиями.

- **Base в G0.** Если блок G0 содержит поле `base_sha`, оно побайтно (40 hex, нижний регистр) равно `base_sha` канонической SPEC из S3. Расхождение → `BLOCKED (base_mismatch)`, даже если `approved_spec_sha256` совпал. Если поля нет, Base утверждён через `approved_spec_sha256` (он входит в SPEC, §4.3 п.4): это записывается в отчёт и провалом не является.
- G0 нет → `BLOCKED (g0_missing)`.
- G0 опубликован агентом или пришёл в relay от агента → недействителен.
- Сообщение координатора «владелец подтвердил в чате» — это квитанция координатора, а не `OWNER-DECISION`. Её можно учитывать как контекст, но G0 она не заменяет.
- Отметка `gate:G0-intake` в Issue — тоже не решение (T35).

**S5. Base и целевая ветка (§4.3).**
- `base_sha` — полные 40 hex.
- `git ls-remote origin refs/heads/<target_branch>` записывается как фактический HEAD.
- `git merge-base --is-ancestor <base_sha> origin/<target_branch>` возвращает 0. Иначе SPEC недействителен → `BLOCKED (base_not_ancestor)`.
- Если целевая ветка ушла вперёд после G0, Base **не меняется** (§4.3 п.7). Это записывается в отчёт, но провалом не является.
- Смена `target_branch` после G0 без нового G0 → `BLOCKED (target_changed)`.
- **Фактическая base ветка PR (§4.3 п.6, T43).** Обязательна в режиме `PRE_HANDOFF`, а в `PRE_WRITE` — как только draft PR задачи открыт. Прочитать у PR задачи поле `base.ref` через API или коннектор, а не из описания PR и не из ASSIGN. Оно должно **точно** совпадать с `target_branch` из последнего действующего G0 (S4).
  - Не совпадает, или PR был перенацелен → `BLOCKED (pr_target_mismatch)` и `STOP`. HANDOFF не публикуется, **даже если ancestry выше дала PASS**: проверка предка не заменяет проверку base PR. Исправить можно двумя способами: вернуть base PR к `target_branch` в пределах ASSIGN, затем заново пройти `PRE_HANDOFF`, или получить новый G0. Сам навык ничего не перенацеливает.
  - ASSIGN или G0 требует PR, а его нет → `BLOCKED (pr_missing)`. PR не требуется и не открыт → `N/A`.
  - Значение `base.ref` перечитывается **непосредственно перед** HANDOFF: прочитанное раньше значение могло устареть.

**S6. CLAIM, ASSIGN и fencing (§0.3, §5.1, §5.2).** Найти все `CLAIM`, `ASSIGN`, `RESUME`, `REASSIGN`, `RELEASE`, `BLOCKED` и `CHECKPOINT` задачи. Порядок определяется по `created_at` GitHub, а не по внутреннему `ts`.

**S6.1. Действующая сессия (effective session).** Сессия, которой разрешено работать, определяется по цепочке `ASSIGN → RESUME…` в порядке `created_at` (§5.2, §5.7, §8.2).

**Применимость S6.1.** Сначала определить, есть ли у задачи **относящееся к ней назначение** — то есть любой `ASSIGN` от `agent: gpt` по этому Task ID, на какую бы сессию он ни был выдан:

- **Назначения нет** — комментариев `ASSIGN` от `agent: gpt` в задаче нет совсем. Сравнивать не с чем: S6.1 → **`N/A (no_assignment)`**. Это разрешено **только** в режиме `READ_ONLY_PREFLIGHT`, то есть для настоящего первого CLAIM. S6 тогда оценивается по строке `READ_ONLY_PREFLIGHT` таблицы ниже, и при остальных `PASS` разрешён ровно один `CLAIM/1`, после чего `STOP` до ASSIGN. `ASSIGN`, опубликованный не от `agent: gpt` (например, исполнителем), недействителен (§5.2): он раскрывается в отчёте и назначением не считается.
- **Назначение прекращено** — каждая цепочка `ASSIGN → RESUME…` от `agent: gpt` явно оборвана: более поздним действительным `REASSIGN` от `agent: gpt` или `RELEASE` её действующей сессии. При этом Issue снова в `status:ready`. Это тоже `N/A (no_assignment)`, только в `READ_ONLY_PREFLIGHT`, для нового заявителя; прежние ASSIGN, REASSIGN и RELEASE раскрываются в отчёте. `BLOCKED` цепочку не прекращает: он ждёт `RESUME`. Любое сомнение, прекращена ли цепочка, означает, что назначение есть.
- **Назначение есть** — тогда S6.1 обязателен в любом режиме, включая `READ_ONLY_PREFLIGHT`, и `N/A` не допускается. Это верно и для `ASSIGN` от `agent: gpt`, который отредактирован, неоднозначен или, возможно, прерван: такой ASSIGN прав не даёт, но и `N/A` не открывает (fail closed). Результат — `STOP` и вопрос координатору.
- В режимах `PRE_WRITE` и `PRE_HANDOFF` отсутствие назначения — это не `N/A`, а `BLOCKED (assign_missing)` / `STOP` (TC-02). В режиме `RECOVERY` действует строка `RECOVERY` таблицы ниже.

Цепочка строится так:

1. Начало цепочки — последний действующий `ASSIGN`: `agent: gpt`, отдельный комментарий, не редактировался, `spec_sha256` = хэш из S3 = G0, `base_sha` = Base. Его `claim_session` — исходная сессия.
2. Каждый **более поздний действительный** `RESUME` заменяет действующую сессию значением своего поля `session`. RESUME действителен, только если выполнено всё:
   - `agent: gpt`. RESUME от любого другого `agent:`, включая опубликованный самим исполнителем, недействителен (§5.7, §8.2);
   - отдельный комментарий, `created_at = updated_at`;
   - опубликован после ASSIGN, с которого начинается цепочка;
   - `assignee` = роль исполнителя (S2);
   - `spec_sha256` = хэш из S3 = G0;
   - поле `session` заполнено и отличается от сессии, которую он заменяет;
   - `head_sha` — полные 40 hex. При первой записи после RESUME он равен `git ls-remote origin <branch>`, позже — предок текущего HEAD;
   - есть `lease_until` (S7).
3. Цепочку прерывают и требуют нового решения координатора:
   - `REASSIGN` → `STOP` для прежнего исполнителя (§8.1). `RELEASE` действующей сессии — отказ от задачи (§5.7). После них цепочка **прекращена**: нужен новый `ASSIGN`, а RESUME после них прав не даёт;
   - более поздний `BLOCKED` → нужен новый действительный RESUME, опубликованный **после** этого `BLOCKED`. Восстановимые случаи — `BLOCKED (lease_expired)` (§8.1), `BLOCKED (session_lost)` и `BLOCKED` с фактическим HEAD впереди, позади или без ветки (§8.2). При другой причине (`spec_changed`, `g0_rejected`, `target_changed` и т.п.) RESUME действителен, только если сама причина устранена и S3–S5 этой проверки дают `PASS`; иначе `STOP`.
4. Недействительный RESUME **игнорируется**: он не передаёт права. Если текущая сессия может опереться только на такой RESUME → `STOP (session_not_assigned)`.
5. Сессия, которую заменил действительный RESUME, становится **устаревшей**: она больше не пишет. Это относится и к исходной сессии из `claim_session`.

**Когда назначение есть**, действующая сессия должна совпасть с фактической сессией из S1. Иначе `STOP (session_not_assigned)`. Это относится к чужой, неизвестной, устаревшей, дочерней (fork), «посеянной» и самовольно возобновлённой сессии. **Когда назначения нет** (`N/A (no_assignment)`, только `READ_ONLY_PREFLIGHT`), сравнение не выполняется и итог не блокирует.

| Режим | Требования |
|---|---|
| `READ_ONLY_PREFLIGHT` | Назначения нет → S6.1 `N/A (no_assignment)`. Своих CLAIM ещё нет: допускается **ровно один**; если свой CLAIM уже опубликован, второй не публикуется. Чужие CLAIM раскрываются. Назначение есть → S6.1 обязателен: ASSIGN на другую сессию, сессия, которую заменил RESUME, или неоднозначный ASSIGN от `agent: gpt` → `STOP`. CLAIM — заявка, а не блокировка. |
| `PRE_WRITE` | Цепочка S6.1 начинается с действующего `ASSIGN`. **Действующая сессия** = фактическая сессия из S1: это `claim_session` ASSIGN или `session` более позднего действительного RESUME. `spec_sha256` ASSIGN и RESUME = хэш из S3 = G0. `base_sha` = Base. `branch` = планируемая ветка. После ASSIGN или последнего действительного RESUME цепочку не прервали `REASSIGN`, `BLOCKED` или `RELEASE` (S6.1 п.3). |
| `PRE_HANDOFF` | Всё из `PRE_WRITE`, включая цепочку S6.1. S3, S4, S5 (base ветка PR) и S7 пересчитаны **непосредственно перед** HANDOFF. HEAD ветки = commit, который будет указан в HANDOFF. Поле `session` HANDOFF = действующая сессия. |
| `RECOVERY` | §8.2: сравнить `head_sha` последнего ASSIGN, RESUME, CHECKPOINT или HANDOFF с `git ls-remote origin <branch>`. В любом случае подготовить `BLOCKED` и ждать `RESUME` от координатора с **новой** сессией. Самостоятельный `RESUME` недействителен. |

ASSIGN без указания сессии → `STOP`. Работать (ветка, файлы, commit, PR, HANDOFF) может только **действующая сессия** из S6.1. Публикация первого `CLAIM/1` в `READ_ONLY_PREFLIGHT` без назначения работой не является и действующей сессии не требует.

**S7. Lease (§8.1).** Применимость зависит от режима:

| Режим | S7 |
|---|---|
| `READ_ONLY_PREFLIGHT`, назначения нет (то же условие, что `N/A (no_assignment)` в S6.1) | **`N/A (no_assignment)`**. Lease появляется только с ASSIGN, поэтому при первом CLAIM его нет. Это не пропущенная обязательная проверка, и PASS она не блокирует. Если назначение есть, `N/A` не допускается: lease действующего ASSIGN или RESUME раскрывается для S6 и S8, а S6.1 решает, можно ли продолжать. |
| `PRE_WRITE`, `PRE_HANDOFF` | **обязательна**: правила ниже. |
| `RECOVERY` | lease записывается в отчёт; работа в любом случае ждёт RESUME. |

Правила, когда действует ASSIGN или RESUME:
- Брать `lease_until` из **последнего** действительного ASSIGN, RESUME или CHECKPOINT **действующей сессии** (S6.1). CHECKPOINT от другой сессии lease не продлевает.
- Сравнивать по UTC в полной точности поля, включая миллисекунды: `now_utc < lease_until` строго. Если `now_utc ≥ lease_until`, lease истёк. Если часам нельзя доверять → `NOT_VERIFIED (clock)`, и для обязательного шага итог `BLOCKED`.
- Срок lease не больше максимума, указанного в Issue или G0.
- CHECKPOINT продлевает lease только до его истечения.
- Истёк → `BLOCKED (lease_expired)` и `STOP`: больше никаких записей. Неявного продления нет, автоматической передачи задачи нет. Если работа не успевает, продление запрашивается у координатора **до** истечения.
- Новый ASSIGN, который сохраняет прежний `lease_until`, срок **не продлевает**.

**S8. Конфликты.**
- Удалённые ветки задачи (`git ls-remote origin`).
- Открытые PR из этих веток.
- Другие открытые Issues в статусах `in-progress`, `handoff`, `qa`: их `Allowed paths` не должны пересекаться с нашими (§4). Пересечение glob-шаблонов, которое не удаётся однозначно исключить, считается конфликтом.
- Локальные worktree (`git worktree list`) и незакоммиченные изменения: чужие не трогать.
- Служебная ветка окружения, если она есть, раскрывается и **не получает** коммитов задачи.

Конфликт → `STOP (conflict)` и раскрытие координатору.

**S9. Пути.** Каждый планируемый к изменению путь входит в `allowed_paths` и **отдельно** сверяется с каждым шаблоном `forbidden_paths`. Совпадение с любым запрещённым шаблоном → `BLOCKED (forbidden_path)`, даже если путь формально подходит под `allowed_paths`. Запрет сильнее разрешения. Совпадение glob, которое нельзя однозначно исключить, считается совпадением. Путь вне `allowed_paths` → `BLOCKED (path_not_allowed)`. Перед HANDOFF то же проверяется для каждого пути `git diff --name-only <base_sha>..<head_sha>`.

## 4. Семантика результатов

| Результат | Значение | Что делать |
|---|---|---|
| `PASS` | проверено по первичному источнику в этой сессии | переходить к следующему шагу |
| `NOT_VERIFIED (<что>)` | проверить не удалось: нет доступа, инструмент запрещён, источник недоступен | для обязательного шага итог — `BLOCKED`; обходов нет |
| `BLOCKED (<причина>)` | предусловия нет или оно изменилось | никаких записей; подготовить черновик `BLOCKED` |
| `STOP` | конфликт, чужая сессия, неясная полномочность | остановиться, раскрыть, ждать координатора |
| `N/A (<почему>)` | шаг к режиму не применим; допускается **только** там, где этот навык прямо его называет: S2 зависимости при `- none`, S5 base PR без PR, S6.1 и S7 до первого ASSIGN (`no_assignment`, только `READ_ONLY_PREFLIGHT`) | записать причину; PASS не блокирует |

Итог отчёта: `PASS`, только если все обязательные для режима шаги S0–S9 дали `PASS` или разрешённый `N/A`. Иначе берётся самый строгий результат (`STOP` > `BLOCKED` > `NOT_VERIFIED`). Если `N/A` указан там, где навык его не разрешает, это `NOT_VERIFIED`.

## 5. Режимы и их границы

- **`READ_ONLY_PREFLIGHT`** — только чтение. Разрешено одно действие записи: **один** `CLAIM/1`, и только если поручение явно просит его опубликовать. После CLAIM — `STOP` до ASSIGN. Ни веток, ни файлов, ни коммитов, ни PR.
- **`PRE_WRITE`** — при `PASS` действующей сессии (S6.1) разрешено то, что прямо перечислено в ASSIGN, а после RESUME — в ASSIGN и действительном RESUME. Обычно это ветка `agent/<agent>/<id-lowercase>` строго от `base_sha`, файлы только из `allowed_paths` (S9) и draft PR с base = `target_branch` (S5).
- **`PRE_HANDOFF`** — при `PASS` разрешён один `HANDOFF/1` по §6. Обязательны: действующая сессия, неистёкший lease и `base.ref` PR = `target_branch`. HANDOFF действует, пока HEAD ветки = `head_sha` (§6.4).
- **`RECOVERY`** — только `BLOCKED` с фактическим HEAD, затем ждать `RESUME`.

## 6. Шаблон отчёта (черновик, в чат или поручающему)

```text

task: <Task ID>  issue: #<n>  mode: <режим>
role: <agent>  session: <фактический id>  source: <как получен>
now_utc: <ISO 8601>
S0 protocol: v1 normative; v2 DRAFT/NOT ACTIVE -> PASS|...
S1 session: <id>; disclosures: <...> -> PASS|NOT_VERIFIED
S2 issue: labels=<...> status_labels=<n, нужен 1> status=<...> dup_search=<n> depends_on=<none|список: статусы> -> PASS|BLOCKED(status_ambiguous|dependency_not_done)
S3 spec: <bytes> bytes, sha256=<64hex>; vector=<PASS|FAIL>; spec_ref=<url> -> PASS|BLOCKED(spec_changed)
S4 g0: decisions=<все G0 по created_at: id, decision, valid> operative=<url> decision=<APPROVE|REJECT|CHANGES> approved=<64hex> g0_base=<40hex|absent> spec_base=<40hex> target_branch=<ветка> -> PASS|BLOCKED(g0_missing|g0_rejected|g0_changes_requested|spec_changed|base_mismatch)|STOP(owner_decision_ambiguous)

S6 fencing: claim=<url|none> assign=<url|none> claim_session=<id|none> resume_chain=<urls|none> effective_session=<id|N/A(no_assignment)> -> PASS|N/A|STOP
S7 lease: lease_until=<ISO|N/A(no_assignment)> source=<url> -> PASS|N/A|BLOCKED(lease_expired)
```

Черновики сообщений `CLAIM`, `BLOCKED` и `RELEASE` составляются по форматам §5.1 и §5.7. Публикуются они только по поручению: отдельным комментарием, без последующей правки. Если внутренний `ts` разошёлся с `created_at`, это раскрывается, а не исправляется.

## 7. Запреты, которые навык не снимает

Нельзя: auto-merge, merge и deploy агентом; G2 и G3; запись `OWNER-DECISION`; правка опубликованных сообщений протокола; изменения вне `allowed_paths`; доступ к production-данным, планшету, GPS, Car-Jukebox, портам и секретам; включение протокола v2; GitHub Actions и автоматическое распределение задач (§0.8).
