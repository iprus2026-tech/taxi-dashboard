# DriverLocationFixV1: контракт качества координат водителя

- Задача: `TAXI-GNSS-QUALITY-01`, milestone 1 (Issue #78)
- Base: `32067e2c0626840b1b7fd56c250ac31bac3af3d1`
- Код: `gnss_quality.py`, тесты: `tests/test_gnss_quality.py`
- Статус: **чистый модуль, не подключён к production.** `app.py`, `static/script.js`, `driver_state.json` и сервер не меняются. Ни один существующий модуль не импортирует `gnss_quality`.

Этот документ не утверждает, что исправлены выводы прежних GPS-диагностик (#13–#17), что реализованы Android GNSS, интеграция с браузером, хранение, офлайн-синхронизация или UAT на планшете. Он описывает формат выборки и правила качества для будущих, отдельно утверждаемых задач.

### 1.3 Риск записи состояния (не устранён этой задачей)

`_write_json` пишет в **фиксированный** путь `driver_state.json.tmp` и делает `os.replace`, **без `fsync`** файла и каталога. Блокировка `_state_lock` (`threading.RLock`, `app.py:51`) действует **только внутри одного процесса**.

Следствия, которые не доказаны как безопасные:

- при нескольких процессах (несколько воркеров WSGI, повторный запуск, внешний скрипт) два писателя используют один `.tmp` и могут затереть друг друга, а цикл «прочитать → изменить → записать» теряет обновления;
- при сбое питания после `os.replace` без `fsync` возможна потеря последних точек или пустой файл, в зависимости от файловой системы.

Для сравнения, запись `yandex_day.json` (`app.py:615–633`) уже использует `mkstemp` + `fsync` + `os.replace`, но тоже без межпроцессной блокировки.

**Поэтому новый приём GNSS-данных поверх `_write_json` в этой задаче не строится.** Безопасный писатель (уникальный временный файл, `fsync`, межпроцессная блокировка или SQLite с транзакциями) — отдельная задача с отдельным утверждением владельца.

## 2. Формат `DriverLocationFixV1`

Один JSON-объект на одно измерение. Неизвестные поля отклоняются (`UNKNOWN_FIELD`). Числа — только JSON-числа: строки, `true`/`false`, NaN, Infinity не принимаются.

| Поле | Обяз. | Тип и единицы | Ограничения |
|---|---|---|---|
| `schema` | нет | строка | если есть, ровно `"DriverLocationFixV1"` |
| `point_id` | да | строка, непрозрачный идентификатор точки | 1–64 символа `[A-Za-z0-9._:-]`, первый — буква или цифра. Генерируется клиентом случайно (например, UUIDv4) для будущей идемпотентности. **Не должен** содержать IMEI, номер телефона, ID устройства, координаты или имя |
| `lat` | да | число, градусы WGS84 | конечное, [−90, 90] |
| `lng` | да | число, градусы WGS84 | конечное, [−180, 180] |
| `captured_at` | да | строка RFC 3339 | `YYYY-MM-DDTHH:MM:SS[.ffffff](Z\|±HH:MM)`; смещение обязательно; не более 6 знаков дроби (больше → отклонение, а не усечение). Приводится к UTC |
| `source` | да | enum | `browser_geolocation`, `android_location`, `external_gnss`, `unknown`. Регистр важен |
| `accuracy_m` | нет, `null` допустим | число, метры, горизонтальный радиус | (0, 100 000]. `0` отклоняется: «идеальная» точность не бывает реальным измерением |
| `speed_mps` | нет, `null` | число, м/с, сообщённое устройством | [0, 120] |
| `heading_deg` | нет, `null` | число, градусы от истинного севера по часовой | [0, 360). `360` отклоняется (не нормализуется молча) |
| `altitude_m` | нет, `null` | число, метры (система высот — как сообщает источник) | [−1 000, 10 000] |
| `altitude_accuracy_m` | нет, `null` | число, метры | (0, 100 000] |
| `new_segment` | нет | bool | клиент явно начинает новый участок (пауза/старт трека) |

Поле **`received_at`** — время получения на сервере. Его передаёт **вызывающий код** (будущий endpoint) аргументом, а не клиент: в теле запроса оно отклоняется. Это делает классификацию детерминированной: модуль сам часы не читает.

Полей спутниковых систем (`constellation(s)`, `satellites_used`, `gnss_system` и т. п.) в v1 нет; они отклоняются с кодом `CONSTELLATION_NOT_SUPPORTED_V1`.

Нормализованная форма (`NormalizedFix.to_dict()`) содержит ровно поля таблицы плюс `received_at`; времена в UTC с `Z`; числа без округления.

### 2.1 Текущий API и предлагаемые поля

| Поле | Сейчас `POST /api/track` | `DriverLocationFixV1` |
|---|---|---|
| координаты | `lat`, `lng` (строки-числа тоже проходят) | `lat`, `lng`, только конечные JSON-числа |
| время измерения | нет | `captured_at` (из `position.timestamp`) |
| время получения | нет | `received_at` от сервера |
| точность | нет (фильтр только в браузере, missing → 0) | `accuracy_m` или `null` |
| скорость/курс/высота | нет | `speed_mps`, `heading_deg`, `altitude_m`, `altitude_accuracy_m`, все `null`-допустимые |
| идемпотентность | нет | `point_id` |
| происхождение | нет | `source` |
| новый участок | `new_segment` | `new_segment` |

Новые поля предлагаются как **опциональные** для будущей версии endpoint'а; существующий API этой задачей не меняется.

## 3. Модель классификации

API модуля:

- `decode_fix_json(raw)` — строгий разбор JSON (без NaN/Infinity, без повторяющихся ключей, UTF-8, ≤ 4096 байт);
- `normalize_fix(payload, received_at=…)` — схема, типы, диапазоны, формат времени;
- `classify_fix(fix, previous, config)` — свежесть и классификация относительно предыдущего якоря;
- `evaluate_fix(...)` = normalize + classify; `evaluate_sequence(...)` — последовательная свёртка с точной суммой (`math.fsum`).

Результат `FixEvaluation` **раздельно** сообщает:

1. `valid_measurement` — прошло ли измерение схему, диапазоны и проверку времени;
2. `distance_contribution_m` — сколько метров фикс добавляет к пробегу (> 0 только у `ACCEPTED_MOVEMENT`);
3. `disposition` + `reasons` — использован, отброшен или подозрителен и почему;
4. `next_anchor` — фикс, который вызывающий код передаёт как `previous` в следующий вызов.

Якорь (`previous`) — последний фикс, принятый как опорная позиция. Модуль не хранит состояние: якорь передаётся явно.

### 3.1 Исходы

| `disposition` | `valid_measurement` | Вклад, м | Якорь |
|---|---|---|---|
| `REJECTED` | false | 0 | не меняется |
| `DISCARDED` | true | 0 | не меняется |
| `SUSPECT` | true | 0 | не меняется |
| `ACCEPTED_SEGMENT_START` | true | 0 | = этот фикс |
| `ACCEPTED_STATIONARY` | true | 0 | не меняется (`STATIONARY_JITTER`) или = этот фикс (`STATIONARY_REANCHOR`) |
| `ACCEPTED_MOVEMENT` | true | haversine до якоря, без округления | = этот фикс |

### 3.2 Порядок проверок и коды причин

1. **Валидация** (`REJECTED`, причины из `issues`, все сразу, в детерминированном порядке): `PAYLOAD_NOT_OBJECT`, `MISSING`, `UNKNOWN_FIELD`, `CONSTELLATION_NOT_SUPPORTED_V1`, `UNSUPPORTED_SCHEMA`, `INVALID_TYPE`, `NOT_FINITE`, `OUT_OF_RANGE`, `INVALID_FORMAT`, `INVALID_VALUE`, `TIMEZONE_NAIVE`, `PRECISION_UNSUPPORTED`, `INVALID_SOURCE`; для сырого JSON: `MALFORMED_JSON`, `DUPLICATE_KEY`, `INVALID_UTF8`, `PAYLOAD_TOO_LARGE`.
2. **Свежесть** (`REJECTED`): `FIX_STALE`, если `received_at − captured_at > max_age_s`; `FIX_IN_FUTURE`, если `captured_at − received_at > max_future_skew_s`. Границы включительно допустимы.
3. **Идемпотентность и порядок** (`DISCARDED`, только при наличии якоря): `DUPLICATE_POINT_ID` (тот же `point_id`, то же содержимое кроме `received_at`), `POINT_ID_CONFLICT` (тот же `point_id`, другое содержимое), `OUT_OF_ORDER` (`captured_at` раньше якоря), `NON_INCREASING_TIMESTAMP` (равно якорю).
4. **Точность** (`DISCARDED`): `ACCURACY_MISSING` (поле отсутствует или `null`; в отличие от `script.js`, не считается нулём), `ACCURACY_INSUFFICIENT` (`accuracy_m > max_accuracy_m`).
5. **Границы участков** (`ACCEPTED_SEGMENT_START`): `FIRST_FIX`, `SEGMENT_REQUESTED` (`new_segment: true`), `GAP_NEW_SEGMENT` (с якоря прошло больше `max_gap_s` и есть перемещение). Если прошло больше `max_gap_s`, но перемещение в пределах дрожания — `STATIONARY_REANCHOR` (стоянка: якорь обновляется, разрыва трека нет).
6. **Дрожание** (`ACCEPTED_STATIONARY`, `STATIONARY_JITTER`): расстояние ≤ `max(min_movement_m, jitter_accuracy_factor × √(acc_prev² + acc_cur²))`. Якорь остаётся, поэтому медленное движение не теряется: оно засчитывается, когда суммарное смещение от якоря превысит порог.
7. **Скачок** (`SUSPECT`, `IMPLAUSIBLE_SPEED`): `max(0, d − √(acc_prev² + acc_cur²)) / Δt > max_speed_mps`. Выброс не двигает якорь. Если вслед за ним реально изменилось положение (например, долгий тоннель), через `max_gap_s` от якоря начнётся новый участок (`GAP_NEW_SEGMENT`) без начисления метров за скачок.
8. Иначе **`ACCEPTED_MOVEMENT`**, `MOVEMENT`, вклад = haversine до якоря.

### 3.3 Настройки по умолчанию (`QualityConfig`)

| Параметр | По умолчанию | Смысл |
|---|---|---|
| `max_age_s` | 300 | старше — `FIX_STALE` |
| `max_future_skew_s` | 5 | допуск расхождения часов |
| `max_accuracy_m` | 80 | совпадает с текущим порогом браузера |
| `max_speed_mps` | 70 (252 км/ч) | порог правдоподобной скорости |
| `max_gap_s` | 120 | разрыв, после которого начинается новый участок |
| `min_movement_m` | 3 | минимальный учитываемый шаг |
| `jitter_accuracy_factor` | 1.0 | множитель суммарной погрешности для порога дрожания |

Все значения — явные параметры неизменяемого (`frozen`) объекта; глобального изменяемого состояния нет. Значения по умолчанию — инженерные исходные точки, **не** откалиброванные на реальных поездках (такая калибровка потребует отдельно утверждённых и обезличенных данных).

Расстояние считается по сфере R = 6 371 000 м, как в `app.py`; это приближение (до ≈ 0,5 % относительно эллипсоида WGS84). Модуль не утверждает, что пробег в production исправлен: он ничего не меняет в смене и не начисляет метры.

## 4. Поздние и офлайн-точки (будущий endpoint, не реализовано)

Будущий постоянный и идемпотентный endpoint (отдельная задача) должен:

1. принимать пакеты точек, накопленных офлайн, с `point_id` и `captured_at` каждой;
2. проставлять `received_at` по серверным часам при приёме пакета;
3. для офлайн-синхронизации использовать отдельный, явно настроенный `max_age_s` (например, длительность смены), а не значение по умолчанию для онлайн-потока;
4. хранить `point_id` с ограничением уникальности (в рамках смены): повтор — ответ «уже принято» без повторного начисления; тот же `point_id` с другим содержимым — конфликт;
5. сортировать пакет по `captured_at` перед свёрткой; точки старше уже сохранённого якоря не пересчитывают пройденный путь задним числом, а помечаются `OUT_OF_ORDER` (возможный будущий режим полного пересчёта участка — отдельное решение);
6. хранить якорь (`next_anchor`) рядом с треком, транзакционно с самой точкой и итогом пробега;
7. работать только поверх безопасного писателя (§1.3).

Модуль уже даёт для этого детерминированную классификацию; хранения, очередей, повторов и сетевой логики в нём нет.

## 5. Происхождение данных и возможности GNSS

- **`browser_geolocation`** — позиция из W3C Geolocation API. Это объединённый (fused) результат ОС и браузера: спутники (GPS, ГЛОНАСС, Galileo, BeiDou), Wi‑Fi, сотовые сети, датчики. API отдаёт координаты, `accuracy`, время и, при наличии, скорость, курс, высоту. **Он не сообщает, какие спутниковые системы и спутники использованы.** Такой фикс нельзя помечать как «GPS» или «ГЛОНАСС/Galileo/BeiDou». `accuracy` — оценка устройства (радиус доверия), а не гарантия.
- **`android_location`** — будущий нативный адаптер Android (`LocationManager`/`FusedLocationProvider`). Сведения о спутниках доступны только через `GnssStatus` / `GnssMeasurement` / NMEA, требуют отдельного разрешения, жизненного цикла и доказательств адаптера. В v1 не реализовано.
- **`external_gnss`** — будущий внешний приёмник (например, NMEA по Bluetooth/USB). Требует подтверждённого протокола, сопряжения и проверки. В v1 не реализовано.
- **`unknown`** — источник не установлен. Вызывающий код обязан выбрать его, если не может доказать иное.

Модуль никогда не выводит `source` из других полей (высокая точность не превращает браузерный фикс в «GNSS»), а поля спутниковых систем в v1 отклоняются при любом `source`. Расширение под спутниковые данные — будущая версия контракта с отдельным утверждением.

Фоновая геолокация в веб-версии не предполагается: `watchPosition` работает, пока страница активна. Сырые спутниковые данные в браузере недоступны.

## 6. Приватность и безопасность

Требования к тестам, CI, отчётам и коду этой задачи:

- только синтетические координаты, построенные арифметически вокруг (0, 0) в открытом океане и на математических границах (полюса, антимеридиан); никаких реальных маршрутов, домашних или рабочих адресов, идентификаторов устройств, токенов и записанных GPS-пакетов;
- модуль ничего не логирует и не печатает; `repr` фикса скрывает `lat`, `lng`, `altitude_m` и `point_id`, чтобы случайный лог не раскрыл позицию;
- модуль не пишет файлы, не открывает сеть и не читает часы.

Ожидания к будущей интеграции (отдельные задачи):

- **согласие и управление пользователем:** сбор координат только после явного старта смены/трека водителем, с видимым индикатором и кнопкой остановки; отказ в разрешении браузера должен корректно останавливать трек, без повторных навязчивых запросов;
- **минимизация:** хранить только поля контракта, без ID устройства, IP в связке с треком и посторонних метаданных;
- **хранение:** определить срок хранения сырых точек (например, до закрытия смены и формирования итогов), после чего удалять или огрублять; итоги пробега хранить отдельно от сырого трека;
- **доступ:** трек — персональные данные водителя; не выгружать его в GitHub, CI, отчёты агентов и логи;
- **без побочных изменений:** никаких изменений настроек планшета, разрешений браузера, портов, серверов, production JSON и баз данных в рамках этой задачи.

## 8. Ограничения milestone 1

- Модуль не подключён ни к одному маршруту, интерфейсу или хранилищу.
- Пороги не откалиброваны на реальных данных.
- Проверка дубликатов и порядка сравнивает только с одним переданным якорём; полная идемпотентность требует хранилища (§4).
- Модель расстояния — сфера; эллипсоидальная геодезия не используется.
- Проверка на реальном планшете, браузере или Android не проводилась и этой задачей не разрешена.

## 9. Запуск тестов

Из корня репозитория:

```bash
python3 -m unittest tests.test_gnss_quality -v
```

```bash
python3 -m pytest tests/test_gnss_quality.py
```

Тесты не требуют Flask, сети, браузера и файлов состояния.
