## 0. Ключевые ограничения (читать первыми)

1. **Общий аккаунт не подтверждает личность.** Все участники (владелец и агенты) пишут в GitHub от одного аккаунта `iprus2026-tech` или через пересылку владельцем. Поэтому автор комментария, issue, commit или PR в GitHub **не подтверждает**, кто его написал, и **никогда не доказывает**, что решение принял владелец. Авторство агента определяется только полем `agent:` внутри блока `agent-msg` и тоже не проверяется технически.
2. **Owner Approval на Stage-B действует только процедурно.** Технической гарантии нет. Поэтому:
   - **запрещены** auto-merge, merge из workflow, бота или агента, а также автоматический deploy в любой форме;
   - merge и deploy выполняет **только владелец лично, вручную**;
   - агент **никогда** не публикует сообщение `OWNER-DECISION` и не пересылает его от своего имени.
3. **CLAIM — это заявка, а не блокировка.** Первый по времени CLAIM **не считается** атомарной блокировкой: из-за общего аккаунта, пересылки и гонок между сессиями она невозможна. Пока нет конкурентно-безопасного механизма, исполнителя **подтверждает координатор** сообщением `ASSIGN` (§5.2). До `ASSIGN` работу начинать нельзя.
4. **Истекший lease не означает передачу задачи.** Задача переходит в `status:blocked`. Сменить исполнителя можно только явным `REASSIGN` от координатора, автоматической передачи нет.
5. **Любой результат = общедоступный адрес + SHA-256.** Локальные пути, scratchpad, ссылки на чат и закрытые хранилища недействительны (§6.3).
6. **Устаревший HANDOFF использовать нельзя.** Если HEAD ветки изменился после HANDOFF, этот HANDOFF, а также все QA-REPORT и OWNER-DECISION, ссылающиеся на него, недействительны (§6.4).
7. **OWNER-DECISION всегда содержит точный SHA.** Без полного 40-символьного git SHA, 64-символьного SHA-256 артефакта вне git или 64-символьного `issue_spec_sha256` (G0) решение недействительно. Решение распространяется только на этот SHA.
8. **Автоматическое распределение задач и GitHub Actions на Stage-B не используются.**
9. **Спецификация задачи неизменна после G0.** На G0 владелец утверждает `issue_spec_sha256` — SHA-256 канонической спецификации задачи (§4.2). Перед `ASSIGN`, `HANDOFF`, QA и G2 хэш пересчитывается по текущему тексту Issue. Если он изменился, задача переходит в `BLOCKED` до нового G0. Из-за общего аккаунта это тоже процедурный контроль (§0.1).
10. **Возобновление работы подтверждает только координатор.** Новая сессия никогда не возобновляет задачу сама (§8.2).
11. **Операционная готовность определяется §13.** На дату R2 labels 17/17 и Issue Form в `main` выполнены. По решению владельца протокол не считается операционно готовым, а пилотные Issues не создаются, пока ревизия R2 (K1–K4) не пройдёт QA и OWNER-DECISION G2.

## 4. Модель задачи

- **ID:** `TAXI-<AREA>-<NN>[.<step>]`. Ставится в начале заголовка Issue: `[TAXI-UI-STYLE-01.2] …`. Перед созданием задачи координатор ищет этот ID среди существующих Issues. Дубликат не создаётся.
- **Ветка:** `agent/<agent>/<id-lowercase>`, ответвляется от `Base SHA` задачи. В неё пишет только подтверждённый исполнитель.
- **Поля:** задаются шаблоном `.github/ISSUE_TEMPLATE/agent-task.yml`: ID, родитель, один агент, зависимости, Base SHA, Allowed paths, Forbidden paths, критерии приёмки, гейты, lease, QA-порт.
- **Пересечения:** у двух задач в `in-progress`, `handoff` или `qa` не может быть общих путей в `Allowed paths`. Это проверяет координатор до `ASSIGN`.
- **Зависимости:** задача переходит в `ready` только когда все зависимости в `status:done`.
- **Спецификация:** задача переходит в `ready` только при утверждённом на G0 `issue_spec_sha256` (§4.2).

### 4.1 Машина состояний

```
backlog ──(координатор: зависимости done, scope не пересекается, spec утверждён на G0)──► ready
ready ──(агент: CLAIM — только заявка)──► ready
ready ──(координатор: ASSIGN по конкретному CLAIM)──────────────────────► in-progress
in-progress ──(исполнитель: HANDOFF)───────────────────────────────────► handoff
handoff ──(координатор: передаёт QA-задаче)────────────────────────────► qa
qa ──(QA-REPORT PASS по действующему HANDOFF)──► owner-gate (если нужен гейт) | done
qa ──(QA-REPORT FAIL)──────────────────────────────────────────────────► in-progress
owner-gate ──(OWNER-DECISION APPROVE <точный SHA>)─────────────────────► done
owner-gate ──(OWNER-DECISION REJECT | CHANGES)─────────────────────────► in-progress | blocked
in-progress ──(lease истёк)────────────────────────────────────────────► blocked
blocked ──(координатор: RESUME тому же агенту | REASSIGN другому)──────► in-progress
любой ──(изменился HEAD после HANDOFF)──────────────────────────────────► in-progress (нужен новый HANDOFF)
любой ──(issue_spec_sha256 ≠ утверждённому на G0)───────────────────────► blocked (нужны новый SPEC и G0)
```

Ни один переход не выполняется автоматически.

### 4.2 Каноническая спецификация и `issue_spec_sha256`

Каноническая спецификация — это однозначная текстовая форма требований задачи. Она описывает **только** следующие поля и в таком порядке:

| Ключ | Источник в Issue Form | Правило |
|---|---|---|
| `task_id` | Task ID | регулярное выражение `^TAXI-[A-Z0-9]+(-[A-Z0-9]+)*-[0-9]{2}(\.[0-9]+)?$` |
| `base_sha` | Base SHA | ровно 40 символов `[0-9a-f]`, нижний регистр |
| `depends_on` | Depends on | Task ID (не номера Issues), без повторов, сортировка побайтно; пусто → `- none` |
| `allowed_paths` | Allowed paths | пути от корня репозитория или glob, разделитель `/`, без `./` и ведущего `/`, без повторов, сортировка побайтно; пусто → `- none` |
| `forbidden_paths` | Forbidden paths | те же правила; список не может быть пустым |
| `acceptance` | Acceptance criteria | элементы `AC-<n>: <текст>`, n = 1..k подряд, порядок по n; текст в одну строку, последовательности пробелов сжаты до одного |
| `gates` | Owner gates required | подмножество `G0-intake`, `G1-design`, `G2-merge`, `G3-deploy` в этом порядке; пусто → `- none` |

Правила байтового представления:
- кодировка UTF-8 без BOM, Unicode NFC, переводы строк только LF, без табуляций;
- первая строка — `TAXI-ISSUE-SPEC/1`;
- скаляр записывается как `ключ: значение`; список — как строка `ключ:`, за которой идут строки `- элемент`;
- в начале и в конце строк нет пробелов, кроме префикса `- ` у элементов списка; пустых строк нет;
- файл заканчивается ровно одним LF;
- `issue_spec_sha256` = SHA-256 этих байтов (`sha256sum spec.txt`).

Остальные поля Issue (Parent, Agent, Lease, QA port, Expected artifacts, заголовок) **не входят** в спецификацию. Координатор меняет их отдельным комментарием, нового G0 это не требует. Ограничения §2 и §7.4 действуют всегда, независимо от спецификации.

**Проверочный вектор.** Это не утверждённая спецификация, а образец, по которому любой участник может проверить свою реализацию канонизации:

```issue-spec
TAXI-ISSUE-SPEC/1
task_id: TAXI-UI-STYLE-01.2
base_sha: 8dc3402f84eb817266360fa83f66f01766ef4bc4
depends_on:
- TAXI-UI-STYLE-01.1
allowed_paths:
- static/style.css
forbidden_paths:
- .github/**
- app.py
- bootstrap_storage.py
- static/mapbox-token*.json
- static/script.js
- storage.py
- templates/index.html
acceptance:
- AC-1: Изменён только static/style.css.
- AC-2: Тестовый критерий для проверочного вектора.
gates:
- G0-intake
- G2-merge
```

Содержимое блока (495 байт, с завершающим LF) → `issue_spec_sha256 = f9b02543d760371607e263bc8b1f00c0e2030b9d074cf159899f7e716e7456cd`.

**Публикация и проверка.**
1. Координатор публикует сообщение `SPEC` (§5.8) с каноническим текстом в блоке `issue-spec` и его хэшем.
2. Владелец на G0 утверждает `approved_spec_sha256`. Одно решение G0 может перечислять несколько задач, например всю декомпозицию пилота, по одной паре `task_id` + хэш на задачу.
3. Каждый, кто проходит контрольную точку, **заново строит** каноническую форму из **текущего** текста Issue и сравнивает её хэш с утверждённым. Контрольные точки: координатор перед `ASSIGN` и `RESUME`, исполнитель перед `HANDOFF`, QA в начале и в конце проверки, владелец перед G2.
4. Хэш не совпал, поле отредактировано или блок `SPEC` изменён → `BLOCKED (spec_changed)`. Работа и передача результата прекращаются до новой пары `SPEC` + G0.
5. Любое изменение требований после G0 (зависимости, пути, критерии, гейты, Base SHA) требует нового `SPEC` и нового G0. Старое решение на новый хэш не распространяется.
6. Авторизация остаётся процедурной (§0.1): хэш доказывает неизменность текста, но не личность того, кто его утвердил.

### 4.3 Выбор Base SHA и целевой ветки

Этот раздел объясняет, как выбираются значение `base_sha` и целевая ветка задачи. Каноническая форма, алгоритм `issue_spec_sha256` и проверочный вектор (§4.2) не меняются. Форматы сообщений (§5) тоже не меняются.

1. **Целевая ветка** — ветка, в которую пойдёт PR задачи. Обычно это `main`. Ветка `checkpoint/taxi-dashboard-current-20261108` допустима только по явному решению владельца: её исходники отличаются от `main` (Mapbox, GPS hotfix, fail-closed хранилище). Целевая ветка **не входит** в Issue Form и в каноническую спецификацию.
2. **Фиксация целевой ветки.** Целевая ветка фиксируется в **OWNER-DECISION G0** задачи: в поле `note` строкой `target_branch: <полное имя ветки>`. Если в G0 этой строки нет, G0 недействителен для `ASSIGN`.
3. **Изменение целевой ветки** после G0 требует **нового решения владельца** (нового OWNER-DECISION G0 с новой строкой `target_branch`) до продолжения работы. До такого решения задача находится в `BLOCKED (target_changed)`, работа и передача результата прекращаются. Если вместе с веткой меняется Base SHA, это ещё и изменение спецификации: нужен новый `SPEC` (§4.2 п.5).
4. **Base SHA** — полный SHA (40 hex) утверждённого базового commit задачи; он закрепляется в спецификации и в `issue_spec_sha256`. Обычно берут HEAD целевой ветки в момент публикации `SPEC`, но действует значение, утверждённое владельцем на G0. Сокращённые SHA, имена веток и значения из примеров или исторических таблиц не допускаются.
5. Base SHA должен быть предком целевой ветки из G0: `git merge-base --is-ancestor <base_sha> origin/<target_branch>` возвращает 0. Иначе `SPEC` недействителен.
6. **Контрольные точки.** Целевую ветку из последнего действующего G0 сверяют те же участники и в тех же точках, что и `issue_spec_sha256` (§4.2 п.3): координатор перед `ASSIGN` и `RESUME`, исполнитель перед `HANDOFF` (base ветка PR = `target_branch`), QA в начале проверки, владелец перед G2.
7. Если после G0 целевая ветка ушла вперёд, Base SHA задачи **не меняется**. Переход на более новую базу — это изменение спецификации (новые `SPEC` и G0).
8. Эталон защищённых файлов для QA вычисляется из Base SHA задачи (§2). Исторические SHA (`8dc3402…`, `fecc5cc…`, `2458564…`, `0f8a939…`) остаются как записи истории и не переписываются и не заменяются текущим SHA `main`.

## 5. Сообщения

Каждое сообщение протокола — это **отдельный комментарий** в Issue с fenced-блоком `agent-msg`. Комментарии Issue и есть журнал действий. Текст вне блока не является частью протокола. Отредактированные блоки недействительны: вместо правки публикуется новый блок.

Общие обязательные поля: `type`, `v: 1`, `task`, `agent`, `session`, `ts` (ISO 8601 UTC).

### 5.1 CLAIM — заявка исполнителя

````
```agent-msg
type: CLAIM
v: 1
task: TAXI-UI-STYLE-01.2
agent: claude-code
session: <id сессии или чата>
ts: 2026-11-09T10:00:00Z
base_sha: 8dc3402f84eb817266360fa83f66f01766ef4bc4
branch: agent/claude-code/taxi-ui-style-01.2
```
````

CLAIM **не даёт права начинать работу**.

### 5.2 ASSIGN — подтверждение координатора

```
type: ASSIGN
task: …
agent: gpt
assignee: claude-code
claim_session: <session из выбранного CLAIM>
spec_sha256: <64 hex, утверждённый на G0>
base_sha: <40 hex>
branch: agent/claude-code/…
lease_until: 2026-11-10T10:00:00Z
```

Правила:
- Перед `ASSIGN` координатор пересчитывает `issue_spec_sha256` по текущему Issue (§4.2). Если хэш не равен утверждённому, `ASSIGN` не выдаётся.
- Работать может только сессия, указанная в `claim_session`. Остальные заявители прекращают работу и публикуют `RELEASE`.
- Если веток или commit'ов больше одного, координатор выбирает одну ветку. Остальные не используются.
- `ASSIGN` тоже не подтверждает личность (§0.1). Это процедурная фиксация решения координатора, а не техническая блокировка.

### 5.3 CHECKPOINT — прогресс и восстановление

```
type: CHECKPOINT
task: … agent: … session: … ts: …
head_sha: <40 hex, последний опубликованный commit>
done: [ … ]
next: [ … ]
lease_until: …
```

CHECKPOINT может продлить lease **только** до истечения текущего lease. После истечения нужен `RESUME` от координатора.

### 5.6 OWNER-DECISION — решение владельца

```
type: OWNER-DECISION
task: …
gate: G0-intake | G1-design | G2-merge | G3-deploy
decision: APPROVE | REJECT | CHANGES
approved_sha: <точный git SHA, 40 hex>        # для кода и PR
approved_sha256: <точный SHA-256, 64 hex>      # для артефакта вне git
approved_spec_sha256: <64 hex>                 # для G0: по одному на task_id
spec_sha256: <64 hex>                          # для G1–G3: хэш, утверждённый на G0
handoff_ref: <ссылка на комментарий HANDOFF>
note: …
```

Обязательные правила:
- G0: обязателен `approved_spec_sha256` (§4.2). G1: `approved_sha256` артефактов. G2/G3: `approved_sha`. Для G1–G3 дополнительно нужен `spec_sha256`, совпадающий с утверждённым на G0. Все значения **в полной длине**; сокращённый SHA, ветка или «последняя версия» не принимаются;
- перед G2 владелец пересчитывает `issue_spec_sha256` по текущему Issue; если он не совпадает с утверждённым, G2 не проводится;
- решение распространяется **только** на указанный SHA; любое изменение требует нового решения;
- G2 APPROVE не выполняет merge, merge владелец делает вручную;
- если `approved_sha` не совпадает с HEAD PR на момент merge, merge не выполняется;
- сообщение публикует владелец лично; если блок пришёл в relay от агента, он **недействителен**;
- GitHub-автор комментария не подтверждает личность владельца (§0.1).

### 5.7 Служебные сообщения

| type | Кто | Смысл |
|---|---|---|
| `RELEASE` | агент | отказ от заявки или задачи; поля: `reason`, `head_sha` |
| `BLOCKED` | любой | остановка; поля: `reason`, `head_sha` |
| `RESUME` | **только** координатор (`agent: gpt`) | продолжение тем же агентом в новой сессии; поля: `assignee`, `session` (новая), `head_sha`, `spec_sha256`, `lease_until`. `RESUME` от любого другого `agent:` недействителен |
| `REASSIGN` | координатор | смена исполнителя (только явно); поля: `from`, `to`, `reason`, `head_sha`, `branch` |

```

```
Сразу после блока `agent-msg` в том же комментарии идёт блок `issue-spec` с каноническим текстом (§4.2). Блок `SPEC` сам по себе ничего не утверждает: утверждение делает только G0.

## 6. Передача результата (HANDOFF)

### 6.1 Формат

```
type: HANDOFF
v: 1
task: TAXI-UI-STYLE-01.2
agent: claude-code
session: …
ts: …
to: deepseek-qa
spec_sha256: <64 hex, утверждённый на G0; пересчитан перед HANDOFF>
base_sha: <40 hex>
head_sha: <40 hex>
branch: agent/claude-code/taxi-ui-style-01.2
changed_files:
  - path: static/style.css
    sha256: <64 hex>
    url: https://github.com/iprus2026-tech/taxi-dashboard/blob/<head_sha>/static/style.css
artifacts:
  - name: mockup-dashboard-1280x800.png
    sha256: <64 hex>
    url: <общедоступный адрес>
self_checks: [ проверено автором: результат ]
not_run: [ что не проверялось, с причиной ]
```

### 6.2 Правила для `changed_files`

- Список = в точности `git diff --name-only <base_sha>..<head_sha>`.
- Каждый путь входит в `Allowed paths` и не входит в `Forbidden paths`.
- `sha256` = `git show <head_sha>:<path> | sha256sum`.

### 6.3 Адрес артефакта (обязательно)

Каждый файл и артефакт сопровождается **адресом, доступным другим агентам**, и **SHA-256**.

Допустимые адреса:
1. permalink на commit: `https://github.com/iprus2026-tech/taxi-dashboard/blob/<40-hex-sha>/<path>` (адрес на ветку не подходит, нужен именно SHA commit'а);
2. вложение в комментарии Issue или PR этого репозитория (`https://github.com/user-attachments/…`).

Недопустимые адреса:
- локальные пути (`/root/…`, `/tmp/…`, `C:\…`, scratchpad);
- ссылки на чат или сессию агента;
- закрытые хранилища без доступа для всех агентов;
- адреса без SHA-256.

Получатель обязан скачать файл по адресу и пересчитать SHA-256. Если хэш не совпал, артефакт недействителен.

### 6.4 Запрет на устаревший HANDOFF

- HANDOFF действует, **только пока** `HEAD` ветки равен `head_sha`.
- Любой новый commit, force-push или rebase после HANDOFF делает его **недействительным навсегда**. Этот HANDOFF нельзя переиспользовать, «продлить» или исправить правкой комментария. Нужен новый HANDOFF с новым `head_sha`.
- QA проверяет `git ls-remote origin <branch>` = `head_sha` **до и после** проверки. Если значения не совпадают, QA-REPORT = `VOID`.
- QA-REPORT и OWNER-DECISION, ссылающиеся на устаревший HANDOFF, недействительны.

## 7. Независимый QA

1. QA получает только HANDOFF и Issue: Base SHA, пути, критерии приёмки. Переписка исполнителя ему не передаётся.
2. Порядок проверки:
   0. `issue_spec_sha256`, пересчитанный по текущему Issue, = `spec_sha256` из HANDOFF = утверждённый на G0 (§4.2);
   1. HEAD ветки = `head_sha` (§6.4);
   2. SHA-256 всех `changed_files` и `artifacts` по их адресам;
   3. `git diff --name-only base..head` ⊆ `Allowed paths`;
   4. защищённые файлы побайтно совпадают с эталоном (§2);
   5. критерии приёмки;
   6. повторная проверка HEAD и `issue_spec_sha256`.
3. **Изолированный запуск:** временный каталог хранилища, без production JSON/SQLite и резервных копий, без настоящего Mapbox-токена.
4. **Порты.** Реестр:

   | Порт | Назначение | Для нового QA |
   |---|---|---|
   | 5000 | production Flask | **запрещён** |
   | 5001 | Mapbox Preview (занят) | **запрещён** |
   | 5002 | зарезервирован | **запрещён** |

   Порт QA указывается в Issue QA-задачи (поле `QA port`). Он не может входить в реестр выше. Перед запуском QA проверяет, что порт никем не занят (`ss -ltn`), и записывает его в QA-REPORT. Работающие сервисы QA не останавливает и не перезапускает.
5. QA не исправляет код. Если проверка провалена, задача возвращается исполнителю.
6. Исполнитель не может проверять свою же задачу.

## 8. Lease и восстановление после обрыва сессии

### 8.1 Lease

- Значение по умолчанию — 24 часа с момента `ASSIGN`, `RESUME` или CHECKPOINT (продление только до истечения).
- По истечении lease координатор ставит `status:blocked` и публикует `BLOCKED` с причиной `lease_expired`.
- **Задача не переходит к другому агенту автоматически.** Дальше два варианта:
  - `RESUME` тому же агенту;
  - явный `REASSIGN` (решение координатора, а для задач с гейтами — с уведомлением владельца).
- После `REASSIGN` прежний исполнитель ничего не пушит в ветку.

### 8.2 Восстановление

Главное правило: **новая сессия никогда не возобновляет работу сама.** Она только фиксирует найденное состояние и ждёт `RESUME` от координатора. Самостоятельно опубликованный `RESUME` (у которого `agent:` не равен `gpt`) недействителен, а работа, сделанная после него, не принимается.

Новая сессия любого агента:

1. Открывает Issue и сверяет labels: `agent:*` совпадает с ней самой, статус `in-progress` или `blocked`.
2. Находит последний `ASSIGN`, `RESUME`, `CHECKPOINT` или `HANDOFF`.
3. Сравнивает `head_sha` из этого сообщения с `git ls-remote origin <branch>`:
   - **совпадают** → публикует `BLOCKED (session_lost)` и ждёт `RESUME` от координатора с новым `session`;
   - **HEAD впереди** → прогресс прежней сессии; ничего не пушит, публикует `BLOCKED` с фактическим HEAD, решение принимает координатор;
   - **HEAD позади или ветки нет** → `BLOCKED`, решение принимает координатор.
4. Работа продолжается только после `RESUME` от координатора, в котором указан новый `session`. Перед `RESUME` координатор пересчитывает `issue_spec_sha256` (§4.2) и сверяет HEAD ветки с `head_sha`.
5. Агенту без доступа к GitHub владелец передаёт «вставку восстановления»: ссылку на Issue и последний блок `agent-msg`.
