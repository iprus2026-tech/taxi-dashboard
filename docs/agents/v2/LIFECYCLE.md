# v2 — Жизненный цикл задачи: CLAIM, ASSIGN, lease, fencing, HANDOFF, RESUME/2

> **Статус: `DRAFT / NOT ACTIVE`.** Действует `docs/agents/PROTOCOL.md` v1. См. [README.md](README.md).

Покрывает: **AC-2** (CLAIM, ASSIGN с привязкой к сессии, lease, fencing, HANDOFF, личный G0 владельца для каждого будущего RESUME/2, без автоматического возобновления) и часть **AC-7** (lease RESUME/2).

Общие ограничения v1 §0 сохраняются: общий аккаунт GitHub не подтверждает личность; merge и deploy делает только владелец вручную; агент никогда не публикует `OWNER-DECISION`; автоматического распределения задач и GitHub Actions нет. Все проверки ниже **процедурные**, это не криптографическая защита.

---

## 1. Сериализация сообщений v2 (`AGENT-MSG/2 FLAT`)

Сообщения `CLAIM/2`, `ASSIGN/2`, `RESUME/2`, `CHECKPOINT/2`, `BLOCKED/2` и `RELEASE/2` сериализуются одинаково:

1. Сообщение — отдельный комментарий Issue с одним fenced-блоком, открытым строкой `` ```agent-msg `` и закрытым строкой `` ``` ``.
2. **Канонические байты** — содержимое между строкой открытия и строкой закрытия (сами строки fence не входят), включая LF перед закрывающим fence.
3. UTF-8 без BOM, Unicode NFC, только LF, без CR и табуляций, без пустых строк, без пробелов в начале и в конце строк, ровно один завершающий LF.
4. Первая строка канонических байтов — литерал `agent-msg`. Эта строка повторяет info-string fence намеренно: она входит в байты и в SHA-256 и отличает v2-тело от v1-тела, где её нет.
5. Каждая следующая строка — `key: value`, ровно один пробел ASCII после двоеточия. Ключи идут строго в порядке схемы сообщения, без пропусков, повторов, неизвестных ключей, вложенных секций и JSON.
6. Нарушение п.3–5 → `CANONICALIZATION_ERROR` (байты) или `SCHEMA_INVALID` (ключи и значения). Сообщение отвергается целиком.
7. Отредактированное сообщение недействительно: `updated_at` ≠ `created_at` после нормализации ([EVIDENCE.md §6](EVIDENCE.md)). Вместо правки публикуется новое сообщение.

Общие грамматики значений:

| Значение | Грамматика |
|---|---|
| session ID | `[A-Za-z0-9._-]{8,128}` |
| comment ref | десятичный ID комментария Issue `[1-9][0-9]*`, полученный GET-запросом из этой же задачи, а не угаданный URL |
| SHA-256 | `[0-9a-f]{64}` |
| git SHA | `[0-9a-f]{40}` |
| время v2 | `YYYY-MM-DDTHH:MM:SS.sssZ`, UTC ([EVIDENCE.md §6](EVIDENCE.md)) |

`HANDOFF/2` и `QA-REPORT/2` содержат списки, поэтому в плоскую форму не укладываются. Этот документ фиксирует их поля и инварианты. Точная проводная сериализация этих двух сообщений — задача будущего валидатора; до неё они не могут быть машинно проверены ([README.md §5](README.md)).

## 2. CLAIM/2 — заявка

```text
agent-msg
type: CLAIM
v: 2
task: <task_id>
agent: <agent>
session: <session ID этой фактической сессии>
ts: <время v2>
issue_spec_sha256: <64 hex, пересчитан агентом по текущему Issue>
base_sha: <40 hex>
work_profile: <CODE_CHANGE/1 | READ_ONLY_EVIDENCE_QA/1>
task_role: <роль из SPEC/2>
branch: <agent/<agent>/<task-id-lowercase> | none>
```

- CLAIM — **только заявка**, а не блокировка и не разрешение на работу (v1 §0.3). До `ASSIGN/2` агент не создаёт ветку, не пишет файлы и не публикует результаты.
- Перед CLAIM агент выполняет read-only preflight: S1–S3 ([PROFILES.md §5](PROFILES.md)) и проверку отсутствия действующего назначения.
- `session` — идентификатор **реальной текущей** сессии. Повторно использовать идентификатор прежней сессии или другой задачи запрещено. Новый чат ИИ — новая логическая сессия.
- Для `CODE_CHANGE/1` `branch` — планируемое имя ветки, которая **ещё не создана**. Для read-only — литерал `none`.

## 3. ASSIGN/2 — назначение, привязанное к сессии

```text
agent-msg
type: ASSIGN
v: 2
task: <task_id>
agent: gpt
coordinator_session: <session ID координатора>
assignee: <agent>
session: <session из выбранного CLAIM/2>
ts: <время v2>
owner_decision_ref: <comment ID личного G0>
claim_ref: <comment ID выбранного CLAIM/2>
issue_spec_sha256: <64 hex>
base_sha: <40 hex>
target_branch: <ветка>
source_ref: <refs/heads/...>
source_sha: <40 hex>
work_profile: <профиль>
task_role: <роль>
branch: <имя ветки | none>
refs_snapshot_sha256: <64 hex, снимок координатора перед ASSIGN>
lease_until: <время v2>
```

Перед публикацией координатор:

1. Заново читает **все** комментарии Issue и собирает все CLAIM/2 по задаче.
2. Пересчитывает `issue_spec_sha256` по текущему Issue: он должен совпасть с `approved_spec_sha256` личного G0 (`owner_decision_ref`). Проверяет строку `target_branch` в `note` G0 ([PROFILES.md §2.5](PROFILES.md)).
3. Проверяет `depends_on` (все `status:done`), ancestry `base_sha`, доступность `source_sha`, отсутствие пересечения `allowed_paths` с задачами в `in-progress`, `handoff` и `qa` (v1 §4).
4. Проверяет независимость роли ([QA-REPORT.md §5](QA-REPORT.md)).
5. Выбирает **ровно одну** заявку. `session` в ASSIGN/2 копируется из выбранного CLAIM/2 байт в байт.

Правила:

- `agent` всегда `gpt`. ASSIGN/2 от любого другого агента недействителен. `coordinator_session` ≠ `session`.
- Работать может только сессия `session`. Другие заявители прекращают работу и публикуют `RELEASE/2`.
- ASSIGN/2 тоже не подтверждает личность: это процедурная запись решения координатора.

## 4. Fencing: `assign_ref`

1. **Fencing-токен** задачи — числовой ID комментария последнего действующего `ASSIGN/2` или `RESUME/2`. GitHub возвращает его **после** публикации. Поэтому токен не может входить в тело своего же сообщения, и его нельзя угадать или вписать заранее.
2. Каждый последующий артефакт исполнителя (`CHECKPOINT/2`, `HANDOFF/2`, `QA-REPORT/2`, `BLOCKED/2`, `RELEASE/2`) указывает `assign_ref`. В `HANDOFF/2` и `QA-REPORT/2` координатор фиксирует ссылку отдельно (`handoff_ref`), см. §7.
3. Новый действующий `ASSIGN/2`, `RESUME/2` или `REASSIGN` координатора по той же задаче **вытесняет** все прежние токены. Сессия со старым токеном немедленно прекращает запись. Любой её артефакт после вытеснения → `ASSIGN_FENCE_STALE`.
4. Назначение — это кортеж `(repo, task_id, session, assign_ref)`. Оно не переносит права на другую задачу, даже если сессия та же.

### 4.1 Двойной CLAIM

CLAIM не атомарен. Если по задаче есть несколько CLAIM/2:

- координатор выдаёт ASSIGN/2 **только одной** сессии (`claim_ref` указывает выбранный CLAIM);
- невыбранные сессии не получают права на работу. Их артефакты → `SESSION_STALE`, они публикуют `RELEASE/2`;
- если по ошибке опубликованы два ASSIGN/2, действует только самый новый корректный. Старший токен → `ASSIGN_FENCE_STALE`, задача переводится в `blocked`, пока координатор явно не подтвердит исполнителя.

## 5. Lease

| Источник lease | Длительность | Продление |
|---|---|---|
| `ASSIGN/2` | `0 < lease_until − ts ≤ PT24H`; значение ставит координатор и фиксирует в сообщении | **не продлевается**. `CHECKPOINT/2` срок не меняет |
| `RESUME/2` | **ровно `PT12H`**: `lease_until = ts + 12 ч` (политика владельца, [G0 #6831274083](https://github.com/iprus2026-tech/taxi-dashboard/issues/26#issuecomment-6831274083), `resume2_lease_duration: PT12H`) | **не продлевается**. Новый период — только новый личный G0 и новый `RESUME/2` |

Общие правила:

1. Абсолютный потолок любого lease v2 — 24 часа. Изменить политику PT12H для RESUME/2 может только владелец новым решением по новой ревизии контракта v2. Координатор не может выбрать, унаследовать или продлить срок в одностороннем порядке.
2. Время сравнивается в UTC. Неизвестное, неразборчивое или отсутствующее время → считается истёкшим (fail closed).
3. Lease истёк → исполнитель **немедленно** прекращает работу и публикует `BLOCKED/2` с `reason: LEASE_EXPIRED`. Задача переходит в `blocked`. Автоматической передачи другому агенту и автоматического продолжения нет (v1 §0.4).
4. Работа, выполненная после истечения lease, не принимается. Отчёт с ней → `STALE`, `VOID`.

## 6. Восстановление: без автоматического возобновления

**Главное правило: новая сессия никогда не возобновляет задачу сама.** Она фиксирует найденное состояние и останавливается.

### 6.1 `CODE_CHANGE/1`

`RESUME/2` для code-задач **не определён**. После потери сессии или истечения lease:

1. Новая сессия выполняет шаги v1 §8.2 п.1–3 (сверка `head_sha` с `git ls-remote origin <branch>`) и публикует `BLOCKED/2` с фактическим HEAD. Она ничего не пушит.
2. Продолжение возможно только через новый личный G0 владельца по этой задаче и новый `ASSIGN/2` координатора на новый CLAIM/2. Новый токен вытесняет старый.
3. Правила v1 §6.4 и §8.2 по HEAD ветки остаются обязательными.

### 6.2 `READ_ONLY_EVIDENCE_QA/1` — `RESUME/2`

Применяется только к задаче с SPEC/2, `work_profile: READ_ONLY_EVIDENCE_QA/1`, `branch_policy: FORBIDDEN` и реальным предыдущим `ASSIGN/2` или `RESUME/2`. Превратить в `RESUME/2` v1 CLAIM, v1-имя ветки, разовую NONWIRE-консультацию или историческую сессию **запрещено**.

**Шаг 1. Остановка.** Сессия потеряна, lease истёк или нужна замена → работа прекращается, публикуется `BLOCKED/2` (`SESSION_STALE` или `LEASE_EXPIRED`).

**Шаг 2. Новая сессия.** Новая фактическая сессия публикует новый `CLAIM/2`, не заявляя унаследованных прав. Этот комментарий станет `claim_ref`.

**Шаг 3. Личный G0 владельца — для каждого RESUME/2.** Владелец лично публикует новый `OWNER-DECISION` по этой задаче, даже если SPEC/2 не менялась:

```text
type: OWNER-DECISION
gate: G0-intake
decision: APPROVE
approved_spec_sha256: <64 hex текущей SPEC/2>
base_sha: <40 hex>
note: |
  target_branch: <значение из SPEC/2>
  resume_of_comment_id: <previous_assign_ref>
  new_session: <session из нового CLAIM/2>
  task_role: <роль из SPEC/2>
  resume2_lease_duration: PT12H
  approve_one_RESUME/2: true
```

- Одно решение разрешает **ровно один** `RESUME/2`.
- Если меняются источник, база, целевая ветка, зависимости, роль, действия или scope, сначала публикуются новая SPEC/2 и новый G0. Старое решение не переиспользуется, история комментариев не правится.
- Решение владельца, которое нельзя независимо установить (например, блок пришёл в relay от агента или подпись общим логином не подтверждена), → `AUTH_ATTESTATION_UNVERIFIED`, STOP.

**Шаг 4. Проверки координатора.** Координатор (и только он) проверяет: свежий G0 из шага 3; новый CLAIM/2 и его сессию; последний предыдущий токен (`previous_assign_ref` не вытеснен); пересчитанную SPEC/2 = G0; `target_branch`; `depends_on` = `done`; независимость роли; ancestry `base_sha` и доступность `source_sha`; полный снимок refs и сравнение с последним доверенным снимком ([PROFILES.md §5.2](PROFILES.md)); последний артефакт прежней сессии (если был) — повторное чтение по ID, `updated_at` и `body_sha256` ([EVIDENCE.md](EVIDENCE.md)).

**Шаг 5. Публикация.** Координатор публикует один `RESUME/2` (§6.3). Его ID комментария становится новым `assign_ref`. Все прежние токены и сессии теряют право записи.

`RESUME/2` не выдаётся, если: нужный для продолжения артефакт устарел, изменён или недоступен; требуется обновление гейта владельца; хоть одна проверка шага 4 не пройдена.

### 6.3 Схема `RESUME/2` (23 обязательных поля)

Первая строка — `agent-msg`, затем ключи строго в этом порядке:

| # | Ключ | Правило |
|---|---|---|
| 1 | `type` | литерал `RESUME` |
| 2 | `v` | литерал `2` |
| 3 | `task` | Task ID текущей SPEC/2 |
| 4 | `agent` | литерал `gpt` (координатор; он **не** выдаёт себя за возобновляемого агента) |
| 5 | `coordinator_session` | session ID координатора |
| 6 | `assignee` | исполнитель, утверждённый в SPEC/2 и G0 |
| 7 | `session` | новая сессия исполнителя = `new_session` из G0 = `session` CLAIM/2 `claim_ref`; ≠ `coordinator_session` |
| 8 | `ts` | фактическое время выпуска, время v2 |
| 9 | `owner_decision_ref` | ID комментария личного G0 из шага 3 |
| 10 | `claim_ref` | ID нового CLAIM/2 |
| 11 | `previous_assign_ref` | ID последнего действующего ASSIGN/2 или RESUME/2 = `resume_of_comment_id` из G0 |
| 12 | `issue_spec_sha256` | 64 hex = пересчёт текущей SPEC/2 = G0 |
| 13 | `base_sha` | 40 hex, как в SPEC/2 |
| 14 | `target_branch` | как в SPEC/2 и G0 |
| 15 | `source_ref` | как в SPEC/2 |
| 16 | `source_sha` | 40 hex, как в SPEC/2 |
| 17 | `task_role` | `EVIDENCE_EXECUTOR` \| `EVIDENCE_REVIEWER` \| `DESIGNER`, как в SPEC/2 и G0 |
| 18 | `branch` | литерал `none` |
| 19 | `last_artifact_ref` | ID последнего артефакта прежней сессии или `none` |
| 20 | `last_artifact_updated_at` | его `updated_at` после нормализации в `.000Z` или `none` |
| 21 | `last_artifact_body_sha256` | `body_sha256` по [EVIDENCE.md §3](EVIDENCE.md) или `none` |
| 22 | `refs_snapshot_sha256` | SHA-256 текущего снимка `TAXI-REFS-SNAPSHOT/1` |
| 23 | `lease_until` | ровно `ts + PT12H`, время v2 |

Тройка `last_artifact_*`: либо **все три** `none` (только если прежнее назначение не создало ни одного артефакта-комментария), либо все три реальные. Смешанные значения → `SCHEMA_INVALID`. Если нужный прежний артефакт недоступен или отредактирован, `RESUME/2` блокируется. Указать `none` вместо него запрещено.

Канонический синтетический пример и его SHA-256 закреплены в [RESUME2-FIXTURE.md](RESUME2-FIXTURE.md). Синтаксически корректный пример **не является** реальным разрешением.

## 7. HANDOFF/2 — передача результата

Поля (`schema: HANDOFF/2`):

| Поле | `CODE_CHANGE/1` | `READ_ONLY_EVIDENCE_QA/1` |
|---|---|---|
| `task`, `agent`, `session`, `ts` | обязательны | обязательны |
| `assign_ref` | токен §4 | токен §4 |
| `spec_sha256` | пересчитан перед HANDOFF = G0 | то же |
| `work_profile`, `task_role` | `CODE_CHANGE/1`, `IMPLEMENTER` | профиль, `EVIDENCE_EXECUTOR` или `DESIGNER` |
| `base_sha` | 40 hex | 40 hex |
| `branch` | реальное имя | `none` |
| `head_sha` | 40 hex HEAD ветки | **отсутствует** (выдумывать `head_sha` запрещено) |
| `source_ref`, `source_sha` | — | обязательны |
| `changed_files` | ровно `git diff --name-only base..head`, с `sha256` и permalink (v1 §6.2) | `[]` |
| `evidence` | permalink + SHA-256 артефактов (v1 §6.3) | список `EvidenceRef/2` ([EVIDENCE.md](EVIDENCE.md)) |
| `source_checks` | — | `before` и `after` ([PROFILES.md §5](PROFILES.md)) |
| `observations` | — | `[{check_id, provenance, confidence_label, reason}]` |
| `completeness` | — | `FULL` \| `INCOMPLETE` |
| `not_run` | `[{check_id, reason_code, reason}]` | то же |

Правила:

1. ID комментария HANDOFF/2 **не входит** в его тело. GitHub возвращает его после публикации. Координатор фиксирует `handoff_ref` отдельно и передаёт его в назначение проверяющего и в QA-REPORT/2.
2. `CODE_CHANGE/1`: HANDOFF/2 действует, пока HEAD ветки = `head_sha` (v1 §6.4 без изменений).
3. `READ_ONLY_EVIDENCE_QA/1`: `completeness: FULL` требует, чтобы каждый обязательный AC был покрыт доступным доказательством правильного типа. `completeness: INCOMPLETE` допустим как честный отчёт об исполнении: `evidence` может быть пустым, но каждый непокрытый обязательный AC перечислен в `not_run` с `reason_code` и текстом. VERIFIED и PASS в таком отчёте не заявляются.
4. `FULL` или `VERIFIED` при отсутствующем обязательном доказательстве, а также `INCOMPLETE` без причины по каждому AC → `SCHEMA_INVALID`.
5. HANDOFF/2 — не QA PASS и не решение владельца. Исполнитель **не** проверяет собственную задачу.

## 8. Служебные сообщения

| type | Кто | Поля после общих (`agent-msg`, `type`, `v: 2`, `task`, `agent`, `session`, `ts`) |
|---|---|---|
| `CHECKPOINT` | исполнитель | `assign_ref`, `head_sha` (code) или `last_artifact_ref` (read-only). **Lease не меняет** |
| `BLOCKED` | любой | `assign_ref` или `none`, `reason` (reason_code из [QA-REPORT.md §4](QA-REPORT.md)) |
| `RELEASE` | исполнитель или невыбранный заявитель | `claim_ref`, `reason` |
| `REASSIGN` | только координатор | формат ASSIGN/2 с `type: REASSIGN`; для задач с гейтами — с уведомлением владельца |

## 9. Машина состояний (без автоматических переходов)

```
backlog ──(координатор: SPEC/2 + личный G0, depends_on done)──────────► ready
ready ──(агент: CLAIM/2 — только заявка)───────────────────────────────► ready
ready ──(координатор: ASSIGN/2 по одному CLAIM/2)──────────────────────► in-progress
in-progress ──(исполнитель: HANDOFF/2)────────────────────────────────► handoff
handoff ──(координатор: назначает независимого проверяющего)───────────► qa
qa ──(QA-REPORT/2 VALID + PASS)────────────────────────────────────────► owner-gate | done
qa ──(QA-REPORT/2 VALID + FAIL)────────────────────────────────────────► handoff (решение владельца) | in-progress
qa ──(QA-REPORT/2 STALE или VOID)──────────────────────────────────────► blocked
in-progress ──(lease истёк | сессия потеряна | токен вытеснен)─────────► blocked
blocked ──(read-only: личный G0 + RESUME/2)────────────────────────────► in-progress
blocked ──(code: личный G0 + новый ASSIGN/2)───────────────────────────► in-progress
любой ──(issue_spec_sha256 ≠ G0 | target_branch ≠ G0)──────────────────► blocked
```

Только координатор меняет статус задачи по политике владельца. QA не может сам перевести `handoff` в `done`.
