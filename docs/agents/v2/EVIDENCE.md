# v2 — Доказательства: EvidenceRef/2, конверт ISSUE_TEXT_LF/1, проверки изменения и нормализация времени

> **Статус: `DRAFT / NOT ACTIVE`.** Действует `docs/agents/PROTOCOL.md` v1. См. [README.md](README.md).

Покрывает: **AC-4** (конверты доказательств, ID комментариев GitHub и проверки изменения, точная байтовая провенанс, итоги VERIFIED / NOT_VERIFIED / STALE) и часть **AC-7** (нормализация `updated_at` в UTC `.000Z` без заявления об аттестации сырых байтов).

---

## 1. Типы `EvidenceRef/2`

| `type` | Обязательные поля | Что хэшируется |
|---|---|---|
| `git_blob` | `repo`, `commit` (40 hex, неизменяемый), `path`, `sha256` | байты `git show <commit>:<path>` |
| `github_attachment` | `url` (точный адрес `https://github.com/user-attachments/…` этого репозитория), `sha256`, `bytes` | оригинальные байты, **самостоятельно** скачанные проверяющим |
| `github_issue_text` | `repo`, `issue_number`, `comment_id`, `evidence_id`, `comment_updated_at`, `body_sha256`, `excerpt_sha256`, `algorithm: ISSUE_TEXT_LF/1` | §3 и §4 |

Общие правила:

- URL без SHA-256 не является доказательством: URL не адресует содержимое. Локальные пути, scratchpad, ссылки на чат и закрытые хранилища недопустимы (v1 §6.3).
- Адрес `git_blob` — permalink на SHA коммита, а не на имя ветки.
- Ранее заявленный digest без прямого доступа проверяющего к байтам — это только `provenance: AGENT_REPORTED`. Он **никогда** не становится VERIFIED молча.
- Скриншот, отрендеренный Markdown или цитата комментария в чате не равны байтам из API.

## 2. Итог проверки одного доказательства

Для каждого `EvidenceRef/2` проверяющий получает ровно один итог `evidence_outcome`:

| `evidence_outcome` | Когда | Как отражается в check ([QA-REPORT.md](QA-REPORT.md)) |
|---|---|---|
| `VERIFIED` | байты получены проверяющим напрямую; SHA-256 пересчитан и совпал; для `github_issue_text` повторное чтение до и после дало одинаковые `comment_id`, `comment_updated_at` и `body_sha256` | `verification_status: VERIFIED` |
| `NOT_VERIFIED` | байты недоступны (403, нет канала, нет прав, ошибка транспорта), конверт некорректен, или digest известен только со слов агента | `verification_status: NOT_VERIFIED`; обязательный check не может быть PASS |
| `STALE` | доказательство было проверено, но изменилось или исчезло: другой `updated_at`, другой `body_sha256`, 404 на ранее закреплённый комментарий | `verification_status: NOT_AVAILABLE`, `reason_code: STALE_EVIDENCE` или `EVIDENCE_DELETED`, `report_validity: STALE`, `verdict: VOID` |

Отдельный случай: байты получены и SHA-256 пересчитан, но **не совпал** с заявленным, а повторное чтение показывает тот же неизменённый источник. Это не STALE: доказательство проверено (`evidence_outcome: VERIFIED` для фактических байтов) и опровергает заявление. Check фиксируется как `COMPLETED + VERIFIED + FAIL`.

## 3. `body_sha256` и граница провенанса (`DECODED_BODY_UTF8/1`)

1. Получить комментарий через официальный GitHub REST API: `GET /repos/{owner}/{repo}/issues/comments/{comment_id}`.
2. Взять строку JSON-поля `body` **после** JSON-декодирования. Отвергнуть: отсутствующий `body`, `null`, не-строку, строку с непарными суррогатами.
3. `body_sha256` = SHA-256 кодировки этой строки в UTF-8 **до** любой нормализации (CRLF остаётся CRLF).
4. **Граница:** `body_sha256` — хэш JSON-декодированного текста, который вернул API. Это **не** аттестация байтов транспорта, байтов JSON-сериализации или байтов хранилища GitHub, и не доказательство авторства. В отчётах этот хэш называется «digest декодированного тела (`DECODED_BODY_UTF8/1`)». Называть его «raw bytes», «исходными байтами GitHub» или «криптографически подтверждённым содержимым» запрещено.
5. Если SPEC/2 требует более сильного байтового канала, а его нет → `NOT_VERIFIED` и STOP. Синтезировать доказательство запрещено.
6. Канал relay (владелец пересылает текст) не даёт байтов API → `NOT_VERIFIED`.

## 4. Конверт `ISSUE_TEXT_LF/1` (комментарий только с доказательством)

Текстовое доказательство публикуется **отдельным** комментарием, в котором нет ничего, кроме конверта. Произвольный Markdown не разбирается.

### 4.1 Грамматика

1. Исходные данные — декодированная строка `body` (§3). Если в ней есть BOM U+FEFF, одиночный CR или переводы строк, отличные от LF и CRLF, → `CANONICALIZATION_ERROR`.
2. Нормализация **только** `CRLF → LF`. `body_sha256` всегда считается по строке до нормализации.
3. После нормализации весь комментарий ДОЛЖЕН быть ровно одним конвертом:
   - первая строка: `BEGIN-EVIDENCE-TEXT/1 id=<token>`;
   - последняя строка: `END-EVIDENCE-TEXT/1 id=<тот же token>`;
   - после строки END ровно один LF и конец данных. Лишняя пустая строка в конце → `CANONICALIZATION_ERROR`;
   - ни вступления, ни приписки, ни Markdown-fence, ни отступов у строк-маркеров.
4. `token`: ASCII `[A-Za-z0-9._-]{8,64}`. Ключ уникальности в задаче — `(repo, issue_number, evidence_id)`, привязанный к одному неизменному `comment_id`. Повторная привязка или второе вхождение любого маркера → `CANONICALIZATION_ERROR`.
5. Payload — нормализованные внутренние строки, соединённые LF, с ровно одним завершающим LF. Размер 1..262144 байт UTF-8, не больше 2000 строк. Payload ДОЛЖЕН содержать хотя бы один байт, отличный от LF: payload из одного `\n` недопустим.
6. Внутри payload запрещена полная строка, начинающаяся с `BEGIN-EVIDENCE-TEXT/` или `END-EVIDENCE-TEXT/`.
7. Payload не обрезается, пробелы не сжимаются, NFC не применяется, HTML-сущности не декодируются, Markdown не рендерится.
8. `excerpt_sha256` = SHA-256 байтов payload.

Комментарий, отредактированный через веб-интерфейс GitHub, может быть изменён самим интерфейсом. Такие преобразования остаются непроверенными: публиковать конверт следует каналом, который сохраняет точную строку.

### 4.2 Проверочные векторы (синтетические)

| Файл | Байт | SHA-256 | Назначение |
|---|---|---|---|
| [`fixtures/evidence-comment-lf.txt`](fixtures/evidence-comment-lf.txt) | 79 | `e0f467e8c57d1aa79810f34eb13e743722eec2624b05e754773e9e1e988a0e8d` | тело с LF → `body_sha256` |
| [`fixtures/evidence-comment-crlf.txt`](fixtures/evidence-comment-crlf.txt) | 83 | `1f0a005aedaf7d88d878b2ca3ca89bd535f60f9e93fd46546dc7279b2e00a240` | то же тело с CRLF → другой `body_sha256` |
| [`fixtures/evidence-payload.txt`](fixtures/evidence-payload.txt) | 11 | `e49c81e2d2f84e259d40e2fb8192f3bcd198b355184845d76d8f58807d0d78ee` | `alpha\nbeta\n` — payload обоих тел, `excerpt_sha256` |

Оба тела дают один и тот же payload, но разные `body_sha256`. Поэтому замена LF на CRLF в уже закреплённом комментарии обнаруживается как изменение (§5).

## 5. Проверки изменения комментария (repeat-fetch)

Каждое доказательство `github_issue_text`, каждое сообщение протокола, на которое ссылается проверка (G0, CLAIM/2, ASSIGN/2, RESUME/2, HANDOFF/2), и последний артефакт в `RESUME/2` проверяются так:

| Шаг | Действие |
|---|---|
| F1 (before) | GET по `comment_id`; записать `id`, `created_at`, `updated_at`, `body_sha256` |
| F2 | выполнить проверку по содержимому |
| F3 (after) | повторный GET по тому же `comment_id`; записать те же поля |
| F4 | сравнить F1, F3 и значения, закреплённые в ссылке (`comment_updated_at`, `body_sha256`) |

Итог:

| Наблюдение | `evidence_outcome` | reason_code |
|---|---|---|
| совпадают `id`, нормализованный `updated_at` и `body_sha256` | `VERIFIED` (если нет других проблем) | — |
| изменился `updated_at` **или** `body_sha256`, даже если извлечённый payload случайно тот же | `STALE` | `STALE_EVIDENCE` |
| 404 на ранее закреплённый комментарий | `STALE` | `EVIDENCE_DELETED` |
| 403, 401, 429, 5xx, таймаут, нет доступа к API | `NOT_VERIFIED` | `EVIDENCE_NOT_ACCESSIBLE` (для вложений — `ATTACHMENT_403`) |
| `updated_at` отсутствует, пуст или не проходит §6 | `NOT_VERIFIED` | `SCHEMA_INVALID` для ссылки |
| сообщение протокола имеет `updated_at` ≠ `created_at` | сообщение **недействительно** (правка запрещена, §1 п.7 [LIFECYCLE.md](LIFECYCLE.md)) | для сообщения — `SCHEMA_INVALID` |

Обходить 403 через другие права, токены или прокси **запрещено**.

## 6. Нормализация времени GitHub (`GITHUB_TS_SECONDS/1`)

GitHub REST API отдаёт `created_at` и `updated_at` с точностью до секунды (`2026-11-12T16:55:03Z`). Поля времени v2 используют формат `YYYY-MM-DDTHH:MM:SS.sssZ`. Преобразование:

### 6.1 Допустимый вход

JSON-строка, которая целиком соответствует

```text
^[0-9]{4}-[0-9]{2}-[0-9]{2}T[0-9]{2}:[0-9]{2}:[0-9]{2}Z$
```

и календарно корректна по григорианскому календарю:

- год 1970–9999; месяц 01–12; день 01..число дней месяца (февраль: 29 только в високосный год — год делится на 4 и не делится на 100, либо делится на 400);
- час 00–23; минута 00–59; секунда 00–59 (секунда `60` отвергается);
- `T` и `Z` — только заглавные; без пробелов, смещений, дробной части.

### 6.2 Преобразование

Заменить завершающий `Z` на `.000Z`. Никакого округления, пересчёта поясов и иных изменений.

### 6.3 Отвергается (а не исправляется)

Отсутствующее значение, `null`, не-строка, пустая строка; дробная часть (`…:03.123Z`, а также `…:03.000Z` как **вход** из GitHub); смещение (`+00:00`, `-05:00`); строчные `t`/`z`; пробел вместо `T`; ведущие или завершающие пробелы; несуществующая дата; секунда 60. Отвергнутое значение → `NOT_VERIFIED` для ссылки, которая от него зависит.

Значение в `.000Z` допустимо как **канонический результат** в сообщениях v2 (например, `last_artifact_updated_at`), но не как исходный секундный вход из GitHub.

### 6.4 Граница провенанса

Нормализованное время — это преобразование JSON-декодированного поля, которое вернул API. Оно **не** подтверждает байты хранилища или транспорта (§3 п.4). Сравнение `before` и `after` делается по нормализованным значениям.

### 6.5 Векторы

| Вход (JSON-строка) | Результат |
|---|---|
| `2026-11-12T16:55:03Z` | `2026-11-12T16:55:03.000Z` |
| `2024-02-29T00:00:00Z` | `2024-02-29T00:00:00.000Z` (високосный) |
| `2000-02-29T23:59:59Z` | `2000-02-29T23:59:59.000Z` (делится на 400) |
| `2026-02-29T12:00:00Z` | отвергается: несуществующая дата |
| `1900-02-29T12:00:00Z` | отвергается: год вне 1970–9999 (и 1900 не високосный) |
| `2026-11-12T16:55:03.123Z` | отвергается: дробная часть |
| `2026-11-12T16:55:03.000Z` | отвергается как вход GitHub (допустим только как канонический результат) |
| `2026-11-12T16:55:03+00:00` | отвергается: смещение |
| `2026-11-12 16:55:03Z` | отвергается: пробел вместо `T` |
| `2026-11-12T23:59:60Z` | отвергается: секунда 60 |
| `2026-11-12t16:55:03z` | отвергается: строчные буквы |
| `null`, `""`, поле отсутствует | отвергается |
