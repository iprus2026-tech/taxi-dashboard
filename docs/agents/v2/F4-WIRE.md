Порядок строгий: **M → W → B → L → K/S → H/Q → X**. Первая найденная ошибка останавливает разбор (§11). Уровни M и X требуют данных вне сообщения; без них валидатор помечает их `NOT_RUN` (§16).

Термины:

- **тело комментария** — строка JSON-поля `body` после JSON-декодирования ([EVIDENCE.md §3](EVIDENCE.md) п.1–2);
- **канонические байты** — UTF-8 строк между строкой открытия и строкой закрытия обёртки (§2), включая LF перед закрывающей строкой. Это единственный объект хэширования сообщения (§12);
- **сообщение** — канонические байты, прошедшие уровни B–Q.

## 2. Обёртка комментария GitHub (уровень W)

Обёртка — только транспорт. Она отделяет канонические байты от остального текста комментария и сама в хэш сообщения не входит.

Тело комментария разбивается на строки **только** по LF (U+000A). На этом уровне CR — обычный символ.

| Код | Правило |
|---|---|
| `F4-W00` | тело отсутствует, `null`, не строка, содержит непарный суррогат (не кодируется в UTF-8) или длиннее 262144 байт UTF-8 |
| `F4-W01` | тело ДОЛЖНО начинаться с позиции 0 строкой, равной ровно `` ```agent-msg ``, за которой идёт LF. Любой текст, пробел, BOM или CR до LF, другой info-string (например `` ```agent-msg v2 ``) → `F4-W01` |
| `F4-W02` | первая следующая строка, которая начинается с `` ``` ``, ДОЛЖНА быть ровно `` ``` `` (закрывающая строка). `` ```` ``, `` ```text `` и подобные → `F4-W02` |
| `F4-W03` | закрывающей строки нет |
| `F4-W04` | после закрывающей строки идёт либо конец тела, либо LF и необязательная **приписка**. Строка, равная ровно `` ```agent-msg ``, в приписке (второе сообщение в том же комментарии) → `F4-W04` |

- **Канонические байты** = UTF-8 всех строк между строкой открытия и закрывающей строкой, каждая со своим LF. Строки fence в них не входят ([LIFECYCLE.md §1](LIFECYCLE.md) п.2).
- **Приписка** ненормативна: валидатор её не разбирает, она не входит в канонические байты и `canonical_sha256`. Она входит в `body_sha256` и в проверку редактирования: правка приписки делает сообщение отредактированным (§10.1, `F4-M02`). Утверждения в приписке ничего не добавляют к сообщению и ничего в нём не отменяют.
- Markdown не рендерится и не интерпретируется. Нормализация CRLF → LF, которую [EVIDENCE.md §4.1](EVIDENCE.md) п.2 допускает для конверта доказательства, к сообщениям **не применяется**. Тело с CRLF не проходит `F4-W01`, потому что строка открытия заканчивается CR.
- Режим `canonical` (§16.2) подаёт на вход сразу канонические байты. Уровень W тогда не выполняется, и тот же CRLF ловит правило `F4-B04`.

Пример (байты пересчитаны автором): тело `BODY-POS-F4-02` = `` ```agent-msg `` + LF, затем 1958 байт вектора POS-F4-02 (§14.2), затем `` ``` `` + LF. Всего **1975** байт, `body_sha256` (`DECODED_BODY_UTF8/1`) `c0c4ba57e63aeeb2090234e82606539039f5d0cce94d22c9ab8d609a7de6df08`. Канонические байты — те же 1958 байт с `canonical_sha256` `36f3b493ed86276770bdfc84649ececddc596a29d15b173329405c0fca6e5669`. Тело с припиской (`` ``` `` + LF + LF + `Non-normative note.` + LF) занимает 1996 байт, `body_sha256` `cb9604e0f02a6685e9fe609b5eb934c6356f7e837f67b66b69ea271d1111f6dd`; канонические байты и `canonical_sha256` те же.

## 3. Байтовые правила (уровень B)

Правила применяются к каноническим байтам **по одному правилу ко всему входу** в порядке таблицы. Срабатывает первое нарушенное правило, даже если дефект другого вида стоит раньше в тексте.

Категории символов и NFC определяются по Unicode **15.1.0** (UCD и UAX #15 этой версии). Так результат не зависит от версии библиотеки: кодовые точки, не назначенные в 15.1.0, отвергаются правилом `F4-B06`.

| Код | Правило |
|---|---|
| `F4-B01` | длина 1..65536 байт |
| `F4-B02` | корректный UTF-8 по RFC 3629: без overlong-форм, без суррогатов U+D800–U+DFFF, не выше U+10FFFF, без обрезанных последовательностей |
| `F4-B03` | нет U+FEFF (BOM) ни в начале, ни в другом месте |
| `F4-B04` | нет CR (U+000D) |
| `F4-B05` | нет TAB (U+0009) |
| `F4-B06` | нет других запрещённых кодовых точек: все `Cc`, кроме LF; `Cf` (в том числе управление направлением текста и U+200B–U+200D); `Cs`; `Co`; `Cn` (не назначенные в 15.1.0, включая noncharacters); `Zl`, `Zp`; любые `Zs`, кроме U+0020 (например U+00A0, U+3000) |
| `F4-B07` | строка в NFC |
| `F4-B08` | последний байт — LF |
| `F4-B09` | нет пустых строк: нет двух LF подряд и LF в позиции 0. Лишний LF в конце — это пустая строка |
| `F4-B10` | ни одна строка не начинается и не заканчивается пробелом U+0020 |
| `F4-B11` | ни одна строка не начинается с `` ``` `` |
| `F4-B12` | не больше 2000 строк; каждая строка без LF не длиннее 2048 байт |

Правила B01–B10 повторяют [LIFECYCLE.md §1](LIFECYCLE.md) п.3 (UTF-8 без BOM, NFC, только LF, без CR и TAB, без пустых строк и пробелов по краям, ровно один завершающий LF) и уточняют, какие символы запрещены. Правила B11–B12 добавлены для этих двух сообщений: B11 исключает ложное закрытие fence, B12 ограничивает размер недоверенного входа. Для FLAT-сообщений действуют правила LIFECYCLE.md §1 без этих уточнений.

**Приоритет пределов размера (исправление P2-QA33-04).** `F4-B01` проверяется **первым** из всех B-правил и только по общей длине. Вход длиннее 65536 байт получает `F4-B01` (`error_line: none`), даже если число строк и длина каждой строки допустимы. `F4-B12` срабатывает только на входе, который прошёл `F4-B01`–`F4-B11`: 2001-я строка или строка длиннее 2048 байт при общей длине ≤ 65536. Пределы списков §7–§8 — отдельные верхние границы, они не суммируются и не заменяют `F4-B01`. Поэтому сообщение, синтаксически корректное по всем спискам, всё равно может нарушить `F4-B01`: вектор NEG-F4-26 (89329 байт, 1418 строк, самая длинная строка 135 байт) → `F4-B01`, а не `F4-B12`. Контроль: NEG-F4-27 (11708 байт, 2001 строка) → `F4-B12`, строка 2001. Сами пределы (65536 байт, 2000 строк, 2048 байт) этой ревизией не меняются.

## 4. Строки и ключи (уровень L)

1. Строка 1 ДОЛЖНА быть ровно `agent-msg` (`F4-L01`). Она повторяет info-string fence и входит в байты и SHA-256, как в FLAT ([LIFECYCLE.md §1](LIFECYCLE.md) п.4).
2. Каждая следующая строка: `KEY ":"`, затем либо конец строки (**пустое значение**), либо ровно один пробел и `VALUE`, первый символ которого не пробел. Ключ заканчивается на **первом** двоеточии строки. Строка без двоеточия, два и больше пробелов после двоеточия → `F4-L02`. Пробел в конце строки ловит раньше правило `F4-B10`.
3. Грамматика ключа (`F4-L03`):

   ```text
   KEY   = SEG *( "." SEG )              ; от 1 до 6 сегментов, не длиннее 128 байт
   SEG   = NAME / INDEX                  ; первый сегмент — NAME
   NAME  = %x61-7A *31( %x61-7A / DIGIT / "_" )     ; [a-z][a-z0-9_]{0,31}
   INDEX = %x31-39 *3DIGIT                          ; [1-9][0-9]{0,3}, без ведущих нулей
   ```

4. `VALUE` не длиннее 1024 байт (`F4-L04`).
5. **Экранирования нет.** Нет кавычек, обратной косой черты, продолжения строки, комментариев, отступов и вложенных блоков. Значение — буквальный остаток строки после `": "`. Символы `"`, `\`, `#`, `- `, `[`, `{` ничего не означают. JSON, YAML и Markdown-списки не разбираются. Например, строка `changed_files: []` проходит уровень L, но получает `F4-K02`: такого ключа в схеме нет.
6. Символ, который нельзя записать в одной строке (LF, CR, TAB, управляющие символы), значением быть не может. Механизма экранирования для таких символов нет.

## 5. Структуры (уровень K)

### 5.1 Скаляр

Одна строка `key: value`.

### 5.2 Список

Список `L` записывается строкой `L.count: N`. Сразу за ней идут элементы с индексами 1..N по порядку. Элемент — запись, поля которой идут строками `L.<i>.<field>: value` в порядке схемы.

- Пустой список — ровно `L.count: 0` без строк элементов. Формы `- none` и `[]` в этих двух сообщениях не используются.
- Элемент с индексом больше N → `F4-K02`. Недостающий элемент → `F4-K04`. Индекс с ведущим нулём ловит раньше `F4-L03`.
- Верхняя граница N задаётся схемой (§7, §8). Превышение → `F4-S06`.

### 5.3 Фиксированная запись

`source_checks.before.<f>`, `source_checks.after.<f>` и `environment.<f>` — записи с фиксированным набором полей. Поля идут в порядке схемы.

### 5.4 Группа `EvidenceRef/2`

Префикс группы `P`: `evidence.<i>` в `HANDOFF/2`, `checks.<i>.evidence` в `QA-REPORT/2`.

1. Только в `QA-REPORT/2`: `evidence: null` ([QA-REPORT.md §2](QA-REPORT.md)) записывается одной строкой `P: none`. Любое другое значение этого ключа → `F4-S02`.
2. Иначе группа начинается строкой `P.type: <значение>`. За ней идут от 0 до 15 строк `P.<name>:` с необязательным значением, где `<name>` — один сегмент `NAME`. Группа заканчивается на первой строке, ключ которой не начинается с `P.`.
3. **На проводном уровне** проверяются только: первая строка группы — `P.type`; синтаксис строк (§4); односегментные имена; не больше 16 строк в группе; уникальность ключей во всём сообщении (§5.5). Нарушение → `F4-K05` (уровень отчёта или сообщения).
4. **Всё остальное** — известный ли `type`, полнота и порядок полей, грамматики SHA-256, git SHA, времени и `algorithm`, пустые значения — это шаг **E1** оценки доказательства ([EVIDENCE.md §2.1](EVIDENCE.md)), а не схема отчёта. Нарушение даёт `evidence_outcome: REJECTED`, `reason_code: EVIDENCE_REF_INVALID` (D06) для check, где стоит ссылка. Отчёт остаётся `VALID`. Так сохраняется приоритет F1/F2: некорректная ссылка не делает отчёт `INVALID`.
5. Пустое значение (`P.comment_updated_at:`) допустимо **только** внутри группы и означает «поле пусто» в смысле D06. Вне группы пустое значение → `F4-S08`.
6. Канонический порядок полей известных типов. E1 требует ровно этих полей в этом порядке, без лишних:

| `type` | Поля после `type`, по порядку ([EVIDENCE.md §1](EVIDENCE.md)) |
|---|---|
| `git_blob` | `repo`, `commit`, `path`, `sha256` |
| `github_attachment` | `url`, `sha256`, `bytes` |
| `github_issue_text` | `repo`, `issue_number`, `comment_id`, `evidence_id`, `comment_updated_at`, `body_sha256`, `excerpt_sha256`, `algorithm` |

### 5.5 Уникальность и порядок

1. Каждый полный ключ встречается в сообщении не больше одного раза (`F4-K01`), в том числе внутри групп.
2. Порядок ключей полностью задан схемой: заголовок, затем поля в порядке §7 или §8, строка `count` списка непосредственно перед его элементами, элементы по возрастанию индекса, поля элемента в порядке схемы.

### 5.6 Алгоритм обхода (детерминированный)

1. **Предварительный проход:** найти повторы полных ключей. Если они есть → `F4-K01` на строке второго вхождения. Из всех таких строк берётся строка с наименьшим номером.
2. **Обход:** ожидаемая последовательность ключей строится по схеме §7 или §8 и по уже прочитанным **дискриминаторам**: `type`, `v`, `schema`, `work_profile` (в `HANDOFF/2`), наличие `head_sha` или `source_checks.before.ts` (в `QA-REPORT/2`), значения `count`, форма `evidence` (null или группа), `report_validity`. Для каждой строки по порядку:
   - ключ равен ожидаемому → проверить значение (уровень S, §6) и перейти дальше;
   - ключ не входит в набор ключей этой схемы и профиля (неизвестный ключ, ключ чужого профиля, индекс больше прочитанного `count`) → `F4-K02`. Пока `type` не прочитан, набором считается объединение ключей §7 и §8;
   - иначе, если ожидаемый ключ встречается во входе позже → `F4-K03` (нарушен порядок);
   - иначе → `F4-K04` (ожидаемый ключ отсутствует).
3. Вход закончился раньше ожидаемой последовательности → `F4-K04`. Последовательность закончилась, а строки остались → `F4-K02`.
4. Ошибка ключа на строке проверяется раньше ошибки значения на той же строке. Значение ключа-дискриминатора проверяется до того, как от него строится продолжение последовательности.
5. **Позиция группы `EvidenceRef/2`** (префикс `P`, §5.4) проверяется раньше правил п.2: ключ, начинающийся с `P.`, кроме `P.type`, а в `HANDOFF/2` ещё и сам ключ `P` → `F4-K05`. В `QA-REPORT/2` ключ `P` — форма null (§5.4 п.1).
6. **Позиция дискриминатора профиля в `QA-REPORT/2`** (§8): ожидаемым ключом считается `head_sha`, если он встречается во входе дальше, иначе `source_checks.before.ts`. Затем действуют общие правила п.2–3.
7. **Несколько нарушений значения в одной строке:** сначала `F4-S08` для пустого значения, затем `F4-S10`, затем остальные коды S по возрастанию номера.

### 6.1 Значения проверок источника `SOURCE-CHECK/1`

Отдельный словарь для полей `s1`–`s6` записей `source_checks` ([PROFILES.md §5](PROFILES.md)). Он не является словарём `reason_code` и в `checks[]` не используется.

| Поле | `before` | `after` |
|---|---|---|
| `s1`, `s2` | `PASS` | `PASS` \| `UNAPPROVED_BASE` |
| `s3`, `s4` | `PASS` | `PASS` \| `STALE_SOURCE` |
| `s5` | `PASS` (снимок получен) | `PASS` (refs не изменились) \| `TARGET_FAST_FORWARD` (только fast-forward цели, PROFILES.md §5.2 «допустимо») \| `STALE_SOURCE` \| `REF_DRIFT_UNEXPLAINED` \| `SCOPE_VIOLATION` |
| `s6` | `PASS` | `PASS` \| `ASSIGN_FENCE_STALE` \| `LEASE_EXPIRED` |

Не `PASS` в `before` означает, что работа не должна была начаться ([PROFILES.md §5](PROFILES.md)). **Первый диагностический код (исправление P2-QA33-03)** определяется только порядком уровней §1 и §11. Столбец `before` — закрытый словарь из одного значения `PASS`. Поэтому любое другое значение в `source_checks.before.s1`…`s6` — например `UNAPPROVED_BASE`, `STALE_SOURCE` или `TARGET_FAST_FORWARD` — отвергается на уровне S кодом **`F4-S02`** на строке этого значения, раньше уровней H/Q. Если неверных значений несколько, срабатывает первая такая строка. До `F4-H04` и `F4-Q07` поля `before.s1`…`s6` доходят только со значением `PASS`, поэтому эти коды для `before` проверяют лишь время и снимки, а не значения проверок. Для не-`PASS` в `before` они не выдаются. Пример CE-BEFORE-CODE = NEG-F4-25 (`before.s1: UNAPPROVED_BASE` в POS-F4-02) → `F4-S02`, строка 16, `SCHEMA_INVALID` → D15. Не `R1`/`UNAPPROVED_BASE`: отчёт отвергается как схема, а не выводит итог из содержания. Значение `after` вне столбца `after` тоже даёт `F4-S02`. Значение из столбца `after`, недопустимое для `HANDOFF/2` (например `after.s3: STALE_SOURCE`), даёт `F4-H04`. Невозможность получить снимок refs не кодируется значением: по PROFILES.md §5.1 это `BLOCKED` без публикации `HANDOFF/2` или `QA-REPORT/2`.

### 9.4 Вывод `report_validity` и `verdict` из содержания (`F4-Q08`)

Правила применяются по порядку QA-REPORT.md §6. Срабатывает первое:

| Шаг | Условие в содержании отчёта | Вывод |
|---|---|---|
| R1 | `after.s1` или `after.s2` = `UNAPPROVED_BASE` | `INVALID`, `verdict` опущен |
| R2 | `reason_code` любого check ∈ {`STALE_SOURCE`, `STALE_EVIDENCE`, `EVIDENCE_DELETED`, `LEASE_EXPIRED`, `SESSION_STALE`, `ASSIGN_FENCE_STALE`, `REF_DRIFT_UNEXPLAINED`} или значение `after` ∈ {`STALE_SOURCE`, `REF_DRIFT_UNEXPLAINED`, `ASSIGN_FENCE_STALE`, `LEASE_EXPIRED`} | `STALE`, `VOID` |
| R3 | `SCOPE_VIOLATION` в check или в `after.s5` | `VALID`, `VOID` |
| R4 | обязательный check с `result` ≠ `PASS` | `VALID`, `FAIL` |
| R5 | выполненный необязательный check (`required: false`) с `FAIL` | `VALID`, `FAIL` |
| R6 | иначе | `VALID`, `PASS` |

R4–R6 используют значения `required`, записанные в отчёте; офлайн-уровень Q их не меняет. Источник `required` (утверждённая SPEC) сверяет уровень X (`F4-X16`). Указанная пара ≠ выведенной → `F4-Q08` (`SCHEMA_INVALID`, D15). Другие причины `INVALID` из QA-REPORT.md §6 п.1 (конфликт интересов, авторизация, схема отчёта или основания) устанавливает внешний валидатор кодами `F4-*`. Отчёт не может сам объявить себя `INVALID` по такому основанию или из-за D06/D07 в check: такая запись не выводится из содержания → `F4-Q08` (NEG-F1-03). Выдавать `SCHEMA_INVALID` за `FAIL` и наоборот запрещено: `INVALID` без verdict — это отказ валидатора, а `VALID` + `FAIL` — принятый отчёт с отрицательным итогом (POS-F4-04).

### 10.3 Алгоритм `F4-X09`: остановка и сравнение (исправление P1-QA33-01, P2-QA33-02)

Алгоритм — это [EVIDENCE.md §2.1](EVIDENCE.md) без изменений. F4 только указывает, что с чем сравнивается. Для каждого элемента `checks.<i>` по возрастанию `i`:

1. **Не оценивается** (`F4-X09` пройден для элемента): `evidence_outcome: none` (check не выполнен или остановлен до оценки ссылки, QA-REPORT.md §2); `evidence: none`; **E1 не пройден**. Последний случай уже проверен офлайн `F4-Q03`: элемент записан как `REJECTED` / `EVIDENCE_REF_INVALID`, FAIL / COMPLETED / NOT_VERIFIED. E2–E8 для него не выполняются, сеть и контекст не нужны, сравнений нет (POS-F4-04, OPT-F4-02). Выполнение E4 для такой ссылки, вывод `STALE` или `F4-X15` из пустого или некорректного поля ссылки запрещены.
2. **E2–E4.** Первый непройденный шаг даёт итог, дальнейшие шаги не выполняются. E2: 404 на закреплённый комментарий → `STALE` / `EVIDENCE_DELETED` (`F4-X15`); иная ошибка доступа → `NOT_VERIFIED` / `EVIDENCE_NOT_ACCESSIBLE` (`ATTACHMENT_403`). E3 → `NOT_VERIFIED` / `EVIDENCE_NOT_ACCESSIBLE` или `EVIDENCE_TS_UNVERIFIABLE`. E4 сравнивает **закреплённые в ссылке** `comment_updated_at` и `body_sha256` с нормализованным `updated_at` и `body_sha256` ответа F1. Несовпадение → `STALE` / `STALE_EVIDENCE` (`F4-X15`), а не D15.
3. **E5** (только `github_issue_text`). Грамматика конверта не пройдена → предварительный итог `REJECTED` / `CANONICALIZATION_ERROR` (D07; для сообщения-предмета это D14 через E5). Payload не извлекается, `excerpt_sha256` не вычисляется и **не сравнивается**: заявленный `excerpt_sha256` может быть любым значением `[0-9a-f]{64}` (POS-F4-06). Переход к п.5.
4. **E6.** Пересчитать `excerpt_sha256` от payload (для `git_blob` и `github_attachment` — `sha256` полученных байтов) и сравнить с **заявленным в ссылке отчёта**. Равны → предварительно E8 (`VERIFIED`). Не равны → предварительно D02: `VERIFIED` фактических байтов, `reason_code: none`, тройка FAIL / COMPLETED / VERIFIED. Это опровержение заявления, а не ошибка схемы (CE-D02-X09 = POS-F4-05).
5. **E7** (после п.3 или п.4). Повторный F3 сравнивается с F1. Различие или 404 → `STALE` (`F4-X15`): этот итог заменяет предварительный итог E5/E6. Совпадение означает **стабильный источник**, и предварительный итог становится окончательным.
6. **Сравнение с записью элемента.** Окончательный итог не `STALE` ⇒ запись должна ему соответствовать, иначе `F4-X09`:

| Вычисленный итог | `evidence_outcome` | `reason_code` | `result` / `execution_status` / `verification_status` | Что **не** требуется |
|---|---|---|---|---|
| E8 (D01, или наблюдаемый провал I4) | `VERIFIED` | `none` | PASS или FAIL / COMPLETED / VERIFIED | — |
| E6 ≠ (D02) | `VERIFIED` | `none` (обязателен текст `reason`, `F4-Q05`) | **FAIL** / COMPLETED / VERIFIED | равенство заявленного и пересчитанного `excerpt_sha256` (`sha256`) |
| E5 (D07 / D14) | `REJECTED` | `CANONICALIZATION_ERROR` | FAIL / COMPLETED / NOT_VERIFIED | вычисление и сравнение `excerpt_sha256` |
| E2 или E3 (D03, D05) | `NOT_VERIFIED` | `EVIDENCE_NOT_ACCESSIBLE`, `ATTACHMENT_403` или `EVIDENCE_TS_UNVERIFIABLE` (тот, что вычислен) | FAIL / COMPLETED / NOT_VERIFIED | E4–E8 |
| digest без доступа к байтам (D04) | `NOT_VERIFIED` | `PRIMARY_SOURCE_UNKNOWN` | FAIL / COMPLETED / NOT_VERIFIED | E3–E8 |

Последствия для итога отчёта. D02, D03–D05, D07 и D14 — классификации уровня доказательства. Отчёт с ними, записанными верно, проходит `F4-X09` и остаётся `VALID`: `FAIL` по R4, если check обязательный, или по R5. Он не получает `INVALID`/D15 и не получает `STALE` (EVIDENCE.md §2.2 правила 1, 6). `F4-X09` (D15) — только расхождение записи с вычисленным итогом, например `PASS` при опровергнутом digest (X-NEG-09) или `VERIFIED` для сообщения-предмета (NEG-D14-01).

**Что X не проверяет.** Совпадение `changed_files` с `git diff`, SHA-256 файлов и доказательств, принадлежность путей `allowed_paths` — это не ошибки разбора и не привязка, а **содержание**. Его проверяет независимый проверяющий в своих check (v1 §7 п.2–3): опровергнутое заявление — D02 (FAIL / COMPLETED / VERIFIED), доказанная запись вне scope — `SCOPE_VIOLATION`. Валидатор формы не выносит продуктовый вердикт.

## 11. Таксономия ошибок разбора `F4-ERR/1` и приоритет

Коды `F4-*` — только **диагностика валидатора** (§16.3). Они никогда не записываются в `checks[].reason_code`, не входят в закрытый словарь [QA-REPORT.md §4](QA-REPORT.md) и не меняют его. Каждый код отображается на существующий `reason_code` и на строку таблицы решений.

| Группа кодов | Класс `reason_code` | Субъект «отчёт» (сам `QA-REPORT/2`) | Субъект «сообщение-основание» (`HANDOFF/2` отчёта; для `ASSIGN/2`, `RESUME/2` и G0 — их собственные правила, `F4-X03`) | `HANDOFF/2` вне отчёта |
|---|---|---|---|---|
| `F4-W00`–`F4-W04`, `F4-B01`–`F4-B12` | `CANONICALIZATION_ERROR` | D16 → `INVALID`, verdict отсутствует | D10 → отчёт `INVALID` | сообщение отвергнуто (LIFECYCLE.md §1 п.6) |
| `F4-L01`–`F4-L04`, `F4-K01`–`F4-K05`, `F4-S01`–`F4-S10`, `F4-H01`–`F4-H04`, `F4-Q01`–`F4-Q09` | `SCHEMA_INVALID` | D15 → `INVALID` | D11 → отчёт `INVALID` | сообщение отвергнуто |
| `F4-M01` / `F4-M02` | `SCHEMA_INVALID` | итог D15 (LIFECYCLE.md §1 п.7) | D13 / D12 → отчёт `INVALID` | сообщение недействительно |
| `F4-X01`–`F4-X15` | по §10.2 | `INVALID` или `STALE` по QA-REPORT.md §6 | — | по §10.2 |
| `F4-X16` | — (кода словаря нет) | `UNRESOLVED`: отчёт не принят, но и не `INVALID`/`FAIL` (§10.2, §19 GAP-F4-REQ-01) | — | — |

**Сообщение — предмет check (D14).** Если `HANDOFF/2` или `QA-REPORT/2` — не основание отчёта, а предмет проверки, F4 к нему как к основанию не применяется. Ссылка `github_issue_text` на его комментарий проходит E1–E8 и при стабильном источнике останавливается на E5: первая строка тела — `` ```agent-msg ``, а не `BEGIN-EVIDENCE-TEXT/1`. Итог D07: `REJECTED` / `CANONICALIZATION_ERROR`, отчёт `VALID` ([EVIDENCE.md §2.2](EVIDENCE.md) правило 6). F4 не создаёт тип ссылки, который давал бы `VERIFIED` для такого предмета.

## 12. Производные величины

| Величина | Определение | Как пересчитать |
|---|---|---|
| `canonical_byte_count` | число байтов канонических байтов, включая завершающий LF | `wc -c` |
| `canonical_sha256` | SHA-256 канонических байтов, 64 строчных hex | `sha256sum` |
| `line_count` | число LF в канонических байтах | `wc -l` |
| `body_sha256` | `DECODED_BODY_UTF8/1` всего тела комментария ([EVIDENCE.md §3](EVIDENCE.md)); включает строки fence и приписку, поэтому ≠ `canonical_sha256` | `sha256sum` от UTF-8 тела |

- Сообщение не содержит собственного `canonical_sha256` и ID своего комментария: их нельзя знать до публикации ([LIFECYCLE.md §4](LIFECYCLE.md) п.1, §7 п.1). Координатор фиксирует `handoff_ref`, а валидатор выводит `canonical_sha256` (§16.3), чтобы QA и владелец могли закрепить его вне сообщения.
- `canonical_sha256` — хэш строки, извлечённой из декодированного `body`. Это не аттестация байтов хранилища GitHub (§0 п.5).
- Все длины и SHA-256 в этом документе пересчитаны автором офлайн. Для проверяющего это `AGENT_REPORTED`, пока он не пересчитает их сам по §14.5.

### 14.5 Офлайн-воспроизведение

Из корня клона на коммите HANDOFF. Нужны только `sed`, `wc`, `sha256sum` (GNU coreutils/sed). Извлечь вектор:

```bash
id=POS-F4-01; sed -n "/^<!-- F4-VECTOR $id BEGIN -->\$/,/^<!-- F4-VECTOR $id END -->\$/p" docs/agents/v2/F4-WIRE.md | sed '1,2d' | sed '$d' | sed '$d' > "$id.txt"
```

Проверить длину и SHA-256:

```bash
wc -c "$id.txt"; sha256sum "$id.txt"
```

То же для `POS-F4-02`, `POS-F4-03`, `POS-F4-04`. Векторы POS-F4-05…07 строятся из них командами §14.6. SPEC/2 §13.1–§13.2 извлекаются так же с маркерами `F4-SPEC SPEC-EX02` и `F4-SPEC SPEC-EX03`:

```bash
id=SPEC-EX02; sed -n "/^<!-- F4-SPEC $id BEGIN -->\$/,/^<!-- F4-SPEC $id END -->\$/p" docs/agents/v2/F4-WIRE.md | sed '1,2d' | sed '$d' | sed '$d' | sha256sum
```

`spec_sha256` в POS-F4-01, POS-F4-02 и POS-F4-04 ДОЛЖЕН совпасть с SHA-256 `SPEC-EX02`, а в POS-F4-03 — с SHA-256 `SPEC-EX03`. Отрицательные векторы §15 строятся из извлечённых файлов `POS-F4-0n.txt` командами из столбца «Построение».

### 14.6 Производные положительные векторы (ревизия #34)

Строятся из `P2` = `POS-F4-02.txt` и `P3` = `POS-F4-03.txt` (§14.5) командами GNU sed. Длина и SHA-256 пересчитаны автором ревизии офлайн. Для проверяющего это `AGENT_REPORTED`, пока он не пересчитает их сам.

**POS-F4-05 = CE-D02-X09** (контрпример P1-QA33-01, независимый QA #6862054097; байты совпали с отчётом QA). Ссылка check заявляет `excerpt_sha256` от `alpha\ngamma\n` (`17cbbec0…953f`). Стабильный payload комментария `12345682` — `alpha\nbeta\n` (`e49c81e2…78ee`), а `body_sha256` и `comment_updated_at` верны. Значит, E4 пройден, E6 опровергает заявление, E7 стабилен, и итог D02 (§10.3 п.4–6). Заявление `17cbbec0…` — синтетическое значение под проверкой, записанное в ссылке отчёта. POS-F4-01 в контексте §13 заявляет верный хэш, поэтому вектор проверяет форму и повторную оценку, а не утверждает ошибку в POS-F4-01. Ровно четыре замены:

```bash
sed -e 's/^checks\.1\.result: PASS$/checks.1.result: FAIL/' -e 's/^checks\.1\.evidence\.excerpt_sha256: .*/checks.1.evidence.excerpt_sha256: 17cbbec0b19b84e7729ef8bba7e45944bfa331f56fa873b4e796d1730b8f953f/' -e 's/^checks\.1\.reason: none$/checks.1.reason: Stable source refutes the declared excerpt hash; D02./' -e 's/^verdict: PASS$/verdict: FAIL/' POS-F4-02.txt > POS-F4-05.txt
```

**POS-F4-06** (D14 через E5, P2-QA33-02). Check ссылается на комментарий-предмет `12345689` (§13) — обычный комментарий `agent-msg`, который не является основанием отчёта. E1–E4 пройдены (закреплённые `comment_updated_at` `2026-11-12T15:01:00.000Z` и `body_sha256` `11a352f2…9968` равны ответу API). E5 не пройден: первая строка — fence. E7 стабилен. Заявленный `excerpt_sha256` оставлен прежним (`e49c81e2…78ee`) и не сравнивается (§10.3 п.3). Десять замен:

```bash
sed -e 's/^checks\.1\.result: PASS$/checks.1.result: FAIL/' -e 's/^checks\.1\.verification_status: VERIFIED$/checks.1.verification_status: NOT_VERIFIED/' -e 's/^checks\.1\.evidence\.comment_id: 12345682$/checks.1.evidence.comment_id: 12345689/' -e 's/^checks\.1\.evidence\.evidence_id: case-0001$/checks.1.evidence.evidence_id: case-d14-01/' -e 's/^checks\.1\.evidence\.comment_updated_at: .*/checks.1.evidence.comment_updated_at: 2026-11-12T15:01:00.000Z/' -e 's/^checks\.1\.evidence\.body_sha256: .*/checks.1.evidence.body_sha256: 11a352f2bad2ac2c30ecb77ee904e64d5c9350e8efed78d224bd0e3e59879968/' -e 's/^checks\.1\.evidence_outcome: VERIFIED$/checks.1.evidence_outcome: REJECTED/' -e 's/^checks\.1\.reason_code: none$/checks.1.reason_code: CANONICALIZATION_ERROR/' -e 's/^checks\.1\.reason: none$/checks.1.reason: Subject agent-msg comment stops at E5 (fence line, no envelope); D14 via E5 = D07./' -e 's/^verdict: PASS$/verdict: FAIL/' POS-F4-02.txt > POS-F4-06.txt
```

**POS-F4-07** (путь UTF-8/NFC, политика владельца п.4). `docs/example.txt` заменён на `docs/пример.txt` (NFC, без комбинирующих знаков) в `changed_files.1.path` и `evidence.1.path`. ## 16. Контракт будущего валидатора

### 16.1 Статус

Валидатор — отдельная будущая задача `CODE_CHANGE/1` с собственной SPEC, личным G0, CLAIM, ASSIGN, независимым QA и G2. Она ДОЛЖНА зависеть от того, что задача-ревизия F4 [Issue #34](https://github.com/iprus2026-tech/taxi-dashboard/issues/34) достигла `status:done`. Исходная задача Issue #32 заблокирована с итогом FAIL и основанием служить не может. Этот раздел описывает контракт, по которому её проверят. Он **не** разрешает писать код, ставить зависимости, создавать workflow или запускать что-либо.

### 16.2 Вход

| Параметр | Значения | По умолчанию |
|---|---|---|
| `input_mode` | `body` (декодированное тело комментария, уровни W–X) \| `canonical` (канонические байты, уровни B–X) | `canonical` |
| `role` | `report` (вход — `QA-REPORT/2`) \| `basis` (вход — `HANDOFF/2` как основание) \| `message` (вход — `HANDOFF/2` вне отчёта) | по `type` |
| `metadata` | `created_at`, `updated_at`, `comment_id`, `issue_number` как JSON-строки и числа GitHub | нет → уровень M `NOT_RUN` |
| `context` | заранее собранный набор только для чтения: текущие тексты Issue задачи и проверяемой задачи, комментарии по ID с метаданными, снимок refs `TAXI-REFS-SNAPSHOT/1`, ответы `git ls-remote` и `git show` | нет → уровень X `NOT_RUN` |

### 16.3 Выход и коды завершения

Валидатор печатает в stdout ровно одну запись `F4-RESULT/1`. Она записана той же строчной грамматикой (§4), только первая строка — `F4-RESULT/1`. Ключи по порядку:

```text
F4-RESULT/1
contract: F4-WIRE/1
input_mode: <body|canonical>
input_bytes: <целое>
canonical_bytes: <целое|none>
canonical_sha256: <64 hex|none>
schema: <HANDOFF/2|QA-REPORT/2|none>
role: <report|basis|message>
result: <ACCEPT|ACCEPT_STRUCTURAL|REJECT|UNRESOLVED>
error: <F4-код|none>
error_line: <номер строки канонических байтов|none>
reason_code: <код закрытого словаря|none>
subject: <report|basis|message|none>
decision_row: <D10|D11|D12|D13|D15|D16|none>
layers.count: 8
layers.<i>.name: <M|W|B|L|K|S|HQ|X>
layers.<i>.status: <PASS|FAIL|NOT_RUN>
```

| `result` | Код выхода | Значение |
|---|---|---|
| `ACCEPT` | 0 | все уровни, включая M и X, `PASS`; W — `PASS` в режиме `body` или `NOT_RUN` в режиме `canonical` |
| `REJECT` | 1 | первая ошибка по §11; `error` и `reason_code` заполнены |
| — | 2 | ошибка вызова (нет входа, неизвестный параметр). Решения о сообщении нет |
| `ACCEPT_STRUCTURAL` | 3 | уровни B–Q `PASS` (W как для `ACCEPT`), M или X `NOT_RUN`. **Не** принятие реального сообщения |
| — | 4 | внутренняя ошибка или превышение ресурсов самим валидатором. Fail closed: принятия нет |
| `UNRESOLVED` | 5 | только `F4-X16`: уровни M–X пройдены, но итог отчёта зависит от необязательности check, которую утверждённая SPEC/2 выразить не может (§19 GAP-F4-REQ-01). `error: F4-X16`, `reason_code: none`, `decision_row: none`, `layers` X — `FAIL`. Fail closed: это **не** принятие, но и не `SCHEMA_INVALID`, `FAIL` или `INVALID`. Нужно решение владельца |

Требования:

1. **Детерминизм.** Одинаковые вход, `metadata`, `context` и версия контракта дают побайтно одинаковую запись `F4-RESULT/1`. В выводе нет текущего времени, путей, случайных значений и данных окружения. Lease сравнивается по `created_at` из `metadata`, а не по часам машины.
2. `reason_code` в выводе — значение закрытого словаря QA-REPORT.md §4 или `none`. Код `F4-*` пишется только в поле `error`. Для `REJECT` `reason_code` ≠ `none`; для `UNRESOLVED` — всегда `none`.
3. Для `ACCEPT_STRUCTURAL` и `REJECT` по уровню X валидатор не пишет `PASS` за непрогнанные уровни: в `layers` они `NOT_RUN`.
4. `error_line` — номер строки канонических байтов (с 1), где находится первый ошибочный байт или ключ, для `F4-B02`–`F4-B07`, `F4-B09`–`F4-B12`, `F4-L*`, `F4-K*`, `F4-S*`. Для `F4-M*`, `F4-W*`, `F4-B01`, `F4-B08`, `F4-H*`, `F4-Q*`, `F4-X*` и для `F4-K04` в конце входа — `none`. Для `F4-B12` — номер 2001-й строки или первой строки длиннее 2048 байт, смотря что раньше.

### 16.4 Безопасность и пределы недоверенного входа

1. **По умолчанию офлайн.** Без отдельного решения владельца валидатор не открывает сетевых соединений. Возможный будущий сетевой режим — только чтение (`GET` комментариев этого репозитория, `git ls-remote`) и только в отдельной задаче с собственным G0.
2. **Никаких записей во внешние системы.** Нет комментариев, правок или реакций в GitHub, изменения labels, создания или обновления refs, коммитов, PR, merge, deploy, вызовов API веток или merge. Нет доступа к runtime, production, портам 5000/5001/5002, хранилищам приложения.
3. **Нет учётных данных.** Валидатор не читает токены, переменные окружения с секретами, конфигурацию `gh`, git credential helpers и файлы ключей. Офлайн-режиму учётные данные не нужны.
4. **Пределы:** тело ≤ 262144 байт (`F4-W00`); канонические байты ≤ 65536 байт (`F4-B01`); ≤ 2000 строк по 2048 байт (`F4-B12`); ключ ≤ 128 байт и 6 сегментов; значение ≤ 1024 байт; списки по §7–§8; группа `EvidenceRef/2` ≤ 16 строк. Вход сверх предела — `REJECT` по соответствующему коду, без частичного разбора.
5. Разбор линейный по длине входа. Не используются `eval`, разбор YAML или JSON тела сообщения, загрузка внешних схем и сущностей. Вход не исполняется. Валидатор не пишет файлы, кроме явно указанного файла вывода.

### 16.5 Контракт исполняемых тестов

1. Тесты будущей задачи ДОЛЖНЫ покрыть каждую строку матрицы [TEST-CASES.md §6](TEST-CASES.md), относящуюся к `HANDOFF/2` и `QA-REPORT/2`, все векторы §14–§15 и проверочные векторы EVIDENCE.md §6.5. Строки матрицы для FLAT-сообщений, SPEC/2, снимка refs и нормализации времени этот контракт не покрывает: их интерфейс, результат и коды выхода задаёт SPEC самой задачи валидатора, а ожидаемая классификация (`reason_code`) берётся из матрицы.
2. Байтовые векторы строятся из этого документа командами §14.5 и §15. Перед использованием их длина и SHA-256 ДОЛЖНЫ совпасть с указанными здесь. При несовпадении тест не запускается, а расхождение — дефект документа.
3. Каждый тест сравнивает поля `result`, `error`, `error_line`, `reason_code`, `subject`, `decision_row` и код выхода с ожидаемыми значениями.
4. Изменение ожидаемого исхода, кода или байтов требует новой SPEC и нового G0 по контракту, а не правки теста. Фикстуры `fixtures/` и `SHA256SUMS` тестами не переписываются.

6. **`required` — из утверждённой SPEC** (прежняя семантика QA-REPORT.md §2; политика владельца п.3). Проводная форма принимает `true` и `false`, `F4-Q02` снят. Автоматического `true` нет. SPEC/2 не умеет выражать необязательность, поэтому отчёт, итог которого от неё зависит, не принимается: `F4-X16` → `UNRESOLVED` (fail closed, GAP-F4-REQ-01, §19). Отчёт, итог которого от `required` не зависит, принимается при любом значении (OPT-F4-01, OPT-F4-02). **`checks`** — ровно AC-1..AC-k проверяемой SPEC (без изменений).
7. **`SOURCE-CHECK/1`** с `TARGET_FAST_FORWARD` — запись классификации «допустимо» PROFILES.md §5.2. Это не член словаря `reason_code` (поддержано, не меняется).
8. **`changed_files`** для `CODE_CHANGE/1` — ровно `git diff --name-only <base_sha>..<head_sha>` (LIFECYCLE.md §7, PROFILES.md §4 п.2; политика владельца п.1). Нового минимума 1, максимума 200 и обязательного `BLOCKED/2`/`RELEASE/2` для пустого diff нет. Сохраняются сортировка побайтно (`F4-H01`), `sha256` и permalink (`F4-S09`), общие пределы размера (`F4-B01`, `F4-B12`). Совпадение с diff проверяет проверяющий как содержание (§10.2).
9. **`not_run.reason_code`** — действующий закрытый словарь QA-REPORT.md §4 (19 кодов), без `none` (политика владельца п.2). Подмножества нет, новых кодов нет, обязательного перевода в `BLOCKED/2` нет.
10. **Пределы списков не суммируются, и `F4-B01` проверяется первым** (исправление P2-QA33-04). Сообщение, где все списки заполнены до предела, может быть длиннее 65536 байт. Тогда первый и единственный код — `F4-B01`, а не `F4-B12` (NEG-F4-26). `F4-B12` достижим только при общей длине ≤ 65536 (NEG-F4-27). Пределы 65536 байт, 2000 строк, 2048 байт, ключ ≤ 128 байт, значение ≤ 1024 байт, `evidence`/`observations`/`not_run` ≤ 100, `checks` ≤ 99 не меняются.
11. **Пути — UTF-8/NFC с безопасной канонизацией** (политика владельца п.4): грамматика `path` §6, адрес — `enc(path)` §6. Ограничения ASCII для путей нет. Безопасность недоверенного входа сохраняется: запрещённые категории Unicode, не-NFC и некорректный UTF-8 отвергает уровень B; `.`/`..`, пустые сегменты, ведущий `/`, `\` и длина > 255 байт отвергает `F4-S07`. Путь, байты которого в Git не в NFC, F4/1 точно представить не может: сообщение обязано быть в NFC (`F4-B07`), а SPEC/1 и SPEC/2 тоже хранят пути в NFC. Такой файл не совпадёт ни с `allowed_paths`, ни с точным diff — это содержание для проверяющего, а не исключение из B07. Грамматика **`check_id`** (`AC-n`; идентификатор `not_run`) не менялась и решением владельца не затрагивалась.
12. **Unicode 15.1.0** и запрет категорий `Cc` (кроме LF), `Cf`, `Cs`, `Co`, `Cn`, `Zl`, `Zp` и не-ASCII `Zs` дают результат, не зависящий от версии библиотеки, и исключают невидимые и направленные символы.
13. **Отображение уровня X на существующие коды**: выдуманные ссылки → `AUTH_ATTESTATION_UNVERIFIED`, настоящее назначение другой задачи или сессии → `SESSION_STALE`, изменившееся после проверки доказательство → `STALE_EVIDENCE` (`F4-X15`), сдвиг HEAD → `STALE_SOURCE`, время позже публикации → `SCHEMA_INVALID`, lease — по `created_at` GitHub. Новых кодов `reason_code` нет. `F4-X16` кода словаря не имеет (`UNRESOLVED`).
14. **Дискриминатор профиля в `QA-REPORT/2`** — наличие ключа (`head_sha` или `source_checks.before.ts`), без нового поля.

16. **Правка самого `QA-REPORT/2`** → `SCHEMA_INVALID` по LIFECYCLE.md §1 п.7 с итогом D15. Таблица D01–D16 не меняется (поддержано, не меняется).

**GAP-F4-REQ-01 (открыт, требует отдельного решения владельца).** QA-REPORT.md §2 берёт `required` из утверждённой SPEC, а грамматика SPEC/2 (PROFILES.md §2.2) не содержит признака необязательного AC. F4 не может вывести `required: false` из SPEC/2, и подставлять `true` ему запрещено (п.3). Принятое fail-closed поведение: если итог отчёта от `required` не зависит, отчёт принимается; если зависит, результат `UNRESOLVED` (§16.3, `F4-X16`), то есть отчёт не принят, но и не классифицирован как `SCHEMA_INVALID`, `FAIL` или `INVALID`. Варианты для владельца (F4 их не выбирает): (а) новая версия SPEC с признаком обязательности, новая SPEC и G0; (б) явное решение, что все AC SPEC/2 обязательны; (в) иное. До решения `UNRESOLVED` остаётся окончательным выходом валидатора для таких отчётов.
